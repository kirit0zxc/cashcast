# statement-operation-conflict-v1 · предложение A027, ACK B ожидается

## Подтверждённая проблема

HTTP/PG probe на отдельной cashcast_test, 24.10 00:48 UTC: первый CSV содержит
bank ID bank-fixed, сумму10000 и остаток10000; второй файл тот же ID, сумму20000
и остаток20000. Оба commit200, второй inserted0/skipped1. В ledger остаётся10000,
но DailyBalance становится20000. Это не ошибка качества модели: источник пропущен
по ID без проверки содержимого. Probe вне Git подтверждает дефект, не готовность.
Внутри одного файла разные payload одного ID тоже нельзя считать обычным дублем.

## Предлагаемое поведение

Новый код ошибки commit: 409 transaction_id_conflict, общее безопасное сообщение
без сырых ID/сумм/назначений. DTO запросов и успешных ответов прежние. Изменение
содержимого банковской операции не является её автоматической коррекцией.

Для операции с external_id сравнивается нормализованный parser payload:
booked_on, amount_minor, direction, currency, counterparty_ref, counterparty_name,
purpose. Это значения после существующего strip/None, ID регистрозависимый.
source_row, import_id, имя файла и ручная/автоматическая категория не входят.
balance_minor — отдельный дневной остаток, в идентичность операции не входит:
при неизменном payload старый механизм приёма подтверждённого остатка сохраняется.

- Один ID с одинаковым payload в файле: обычный duplicate_in_file, commit skip.
- Один ID с разным payload в файле: failed preview с безопасной row error;
  никаких операций этого файла не подтверждать, commit409 import_failed.
- Уже сохранённый ID с тем же payload: skip, без изменения категории/allocations.
- Уже сохранённый ID с иным payload: commit409 transaction_id_conflict, целиком
  rollback файла, включая новые операции и остатки. Первую запись не перезаписывать.
- Проверка в commit под тем же account lock перед любыми вставками/обновлениями;
  два одновременных файла не обходят ограничение. В preview можно ещё не знать
  конкурирующий commit, поэтому итоговая проверка обязательна именно в commit.
- Операции без external_id сохраняют прежний fingerprint. Не пытаться эвристически
  объединять два законных платежа; проблема неоднозначных банковских ID не решается
  выдуманным ID или нечётким сравнением суммы/контрагента.

Миграция не нужна: поля источника уже хранятся. Fingerprints и старые run/input
не переписываются. Никакого изменения чистых аналитических DTO/категоризатора.
Будущая явная коррекция банковских фактов требует отдельной истории и согласования.

## Проверки перед READY

Изменение каждого поля payload; идентичный overlap; ручная категория сохраняется;
duplicate/conflict внутри файла; конфликт плюс хорошая новая строка даёт полный
rollback; остатки и существующие allocations неизменны; параллельные commit;
старые короткие/длинные bank ID, imports/frozen/scenarios/resource tests.

Связанный mapping-v1 остаётся отдельным предложением. До ACK или полностью
выполненного fallback-протокола это проект решения, а не реализованный контракт.
