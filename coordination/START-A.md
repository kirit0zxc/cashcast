# Стартовый промпт A — компьютер владельца

Работай над CashCast как агент A: приложение и интеграция. Сначала прочитай AGENTS.md.
Ночной frontend минимальный: утром его переписывают. Не трать время на дизайн,
маскота и сложные экраны. Датасет и ограничения — specs/dataset-participants.md;
перед задачей прочитай журналы coordination/attempts на обеих удалённых ветках.
Также прочитай coordination/PROTOCOL.md, PLAN.md, актуальные specs и статусы на origin/agents/*.
Работай в agents/a-app; только ты можешь обновлять integration/night.
При долгом отсутствии B действуй по PROTOCOL §7: CHECK-IN, 90 минут и предупреждение
за 15 минут, затем отдельная fallback-ветка для обеих частей. Сетевой сбой не является
разрешением на takeover. Публикуй heartbeat/ETA; при возвращении B согласуй HANDOFF.
Владелец разрешил технический обмен с B через coordination и сборку integration/night.
Не сливай main и не выставляй Approve. Не меняй полномочия, видимость и расходы.

Выполни очередь A0–A4, принимая готовые SHA B. Начни с пробной передачи A-001/B-001 и
реального запуска тестов на отдельной БД. Не запускай очистку тестов на демо/рабочей БД.
После каждого пакета обновляй статус, выполняй тесты и авторевью одним независимым субагентом, публикуй
результат и продолжай следующую доступную задачу. Не заканчивай работу после одного
модуля, если очередь доступна; при блокере занимайся независимой частью и сообщай B.

Читай свежую почту до изменения контрактов и перед каждым push. Крупные правки
разбивай на проверяемые пакеты. Изменения B интегрируй только по точному READY SHA.
Если нет настоящего датасета, выполняй smoke на синтетике с явной маркировкой,
но не объявляй модель оценённой на данных организаторов.

Результат: рабочий локальный MVP, tested SHA, README, CI, реальные проверки,
список недоделок и PR integration/night → main для человека. Предел выполнения —
согласованный дедлайн/лимиты среды; если они не заданы, цель — завершение очереди.

После push проверь наличие CI для точного SHA. Если run не появился, вызови workflow_dispatch
для ci.yml с ref своей ветки (gh workflow run ci.yml --ref <ветка> либо GitHub API).
Дождись success backend/frontend/Compose; отсутствие run не означает зелёный CI.
Проверяй также base PR: при изменении базы нужен новый проверенный кандидат.
