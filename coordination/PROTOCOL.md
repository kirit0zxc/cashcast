# Протокол ночной работы A/B

Статус: схема согласована владельцем 23.10.2026. Ночные агенты ещё не запущены.
Кто A: агент на компьютере владельца. Кто B: агент на компьютере Димы.
Авторизован технический обмен статусами и предложениями внутри этого приватного
репозитория; сообщения другим людям и сервисам не требуются.

## 1. Ветки и единственный интегратор

- main: исходная точка; утром PR одобряет человек.
- agents/a-app: пишет только A.
- agents/b-analytics: пишет только B.
- integration/night: пишет только A, собирает проверенные SHA обеих веток.
- Исходный SHA bootstrap записать в PLAN после первого commit.
- Каждый работает в своём клоне/рабочем каталоге. Не использовать общую сетевую папку.
- Ни reset чужой работы, ни force push. При non-fast-forward сначала fetch и разбор.

Принятие B: A получает READY с SHA, делает временную локальную ветку от актуальной
integration/night, вливает этот SHA без squash/cherry-pick, проверяет общий код локально,
публикует кандидат в agents/candidate-<id> и открывает PR в integration/night.
CI для PR проверяется на точном head и неизменной базе; после зелёного результата
A fast-forward обновляет integration/night. При изменении базы кандидат и CI повторяются. Не прошедший кандидат не публикуется
как готовый; исправления возвращаются владельцу. Так общая история сохраняет принятые
коммиты и не порождает повторное применение патчей. A аналогично принимает свою ветку.

B перед новой задачей вливает актуальную integration/night в свою рабочую ветку
с чистым рабочим деревом. Не делает этого посреди незакоммиченных правок.
CI запускается для PR и push в integration/night. Каждый пакет имеет отдельный PR
в integration/night либо ясный READY-пакет; финальный PR integration/night → main
остаётся без автоматического merge.

## 2. Кто какие файлы меняет

A: frontend/**; backend/app/core/**; backend/app/api/**; backend/app/main.py;
backend/app/worker.py; backend/app/scripts/**; backend/app/modules/imports/**;
backend/app/modules/jobs/**; backend/app/modules/forecasting/snapshot.py;
backend/migrations/**; backend/alembic.ini; backend/migrate_and_seed.sh;
backend/Dockerfile; infra/**; .github/**; manifests и lock-файлы; общие tests/conftest;
README; specs/api.md, data-model.md, architecture.md, openapi.json и examples.

B: backend/app/modules/forecasting/** кроме snapshot.py;
backend/app/modules/categorization/**; backend/app/modules/planning/**;
evaluation/**; backend/tests/analytics/**; specs/forecasting.md;
specs/categorization.md; specs/planning.md.

Остальные файлы по умолчанию у A; B запрашивает передачу конкретного пути.

Общий backend/app/modules/contracts.py редактирует только A после согласования B.
Новая зависимость/миграция/публичный DTO: B описывает запрос, A вносит изменение.
Не перехватывать чужую область по одному лишь устаревшему heartbeat. Если партнёр
недоступен — независимые задачи или локальное предложение в отдельной ветке.

## 3. Общая память без конфликтов

- PLAN.md — цель, порядок и критерии; меняет A.
- decisions/*.md — решения по контрактам; A фиксирует, B подтверждает точный ID/версию.
- A.md — статус и сообщения A; меняет только A в agents/a-app.
- B.md — статус и сообщения B; меняет только B в agents/b-analytics.
- attempts/A.md и attempts/B.md — опыт попыток, каждый пишет только свой файл.
  До задачи читать связанное с ней из обеих удалённых веток. Повтор неудачи только
  с причиной: изменены условия, устранён дефект или проверяется гипотеза.
- reviews/ — уникальные файлы по роли/пакету; результаты ревью и команд тестирования.
- Обсуждение: добавляем сообщение с ID и reply_to в собственный статус. Чужой файл
  не редактируем. Для status-only пакетов проверка одного ревьюера относится только к корректности метаданных,
  полномочий и SHA; повторять все продуктовые тесты без изменений кода не нужно.
  Пакет сообщений переносится в архив при разрастании; в статусе
  остаются актуальная задача, непрочитанные вопросы и ссылки.

Нельзя читать только локальную копию: она может отставать. Перед задачей/push:

```sh
git fetch origin
git show origin/agents/a-app:coordination/A.md
git show origin/agents/b-analytics:coordination/B.md
git show origin/integration/night:coordination/PLAN.md
git ls-tree -r --name-only origin/agents/a-app -- coordination/decisions
# Затем git show origin/agents/a-app:<путь нужного решения>
```

Если ветки ещё нет — bootstrap не завершён, не выдумывать статус. При ошибке сети
использовать последний известный контракт для независимой локальной работы, но не
считать сообщения доставленными. Подтверждение доставки — запись ACK в статусе второго.

Шаблон сообщения:

```text
ID: B-001
reply_to: none
task: B2
type: proposal | ack | blocked | ready | integrated
contract_version: v1
base_sha: ...
code_sha: ...
request: добавить nullable warning в ForecastResult
affected_files: backend/app/modules/contracts.py
tests: точная команда и результат, либо NOT RUN
```

code_sha — коммит кода; следующий status-only commit может ссылаться на него. Нельзя
вписать в файл SHA содержащего его самого коммита. Интегратор проверяет diff между
code_sha и head: только разрешённые метаданные, либо повторное ревью новой версии.

Статусы: TODO → WORKING → READY → INTEGRATED → VERIFIED; отдельно BLOCKED.
READY означает «тесты и авторевью закончены», VERIFIED — сквозная проверка объединённого
кода. Временная метка пишется в UTC ISO 8601. Часы без сообщения не означают успех.

## 4. Цикл работы

1. Fetch и прочитать сообщения/решения; ACK входящих запросов.
2. Выбрать небольшую задачу из своей очереди; опубликовать WORKING до большой работы.
3. Реализовать в своей области, обновить тесты и спецификацию.
4. Провести локальные проверки и проверку одного независимого ревьюера; исправить замечания.
5. Повторить fetch: проверить изменения контракта, базы и новые сообщения.
6. Commit, status с SHA, push своей ветки; READY или WIP/BLOCKED без приукрашивания.
7. A собирает кандидат, проверяет совместимость и публикует INTEGRATED/VERIFIED.
8. Следующая независимая задача. При ожидании — проверять почту между шагами и примерно
   раз в 5–10 минут, не бесконечно опрашивать GitHub. Ограниченные повторы при сбое сети.

## 5. Никакой магии автопродолжения

AGENTS.md и память — инструкции, не планировщик. Оба активных запуска должны быть
заданы до сна. Отключить сон ПК, проверить Docker, GitHub-доступ, сеть и разрешения
на реальные команды заранее. Не отключать все защиты ради автономности.
Новый комментарий/файл не возобновляет завершённый чат автоматически. Если нужен
автоперезапуск, его настраивают отдельно с ограничением времени/попыток; сейчас такого
механизма нет. При лимите/запросе разрешения возможна остановка.

## 6. Перед сном и утром

Обязателен пробный цикл: A публикует сообщение → B читает и ACK → B делает маленький
пакет → A принимает точный SHA → CI integration проходит → оба восстанавливают контекст
по файлам. Только после этого запускать длинные задачи.

Утром: README с командами, точный tested SHA, статус CI, рабочий демосценарий, измеренные
метрики либо честный блокер датасета, список незавершённого, один итоговый PR в main.
Человек решает merge. Ручное изменение полномочий не прячется в техническом ACK.
