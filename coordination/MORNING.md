Продуктовая версия: A31 `ede8edcb8ca94a657eeb14e22b0ef8e37511371a`.
Общая ветка — `integration/night`; итоговый [PR19](https://github.com/kirit0zxc/cashcast/pull/19)

## Открыть и попробовать

На компьютере владельца уже работает **http://localhost:18086**.
Вход: `demo@example.com` / `demo-password` — локальная демо-учётка.
Для нового клона запуск на8080 описан в [README](../README.md); нужен Docker Desktop
с Linux-контейнерами, Python/Node для обычного Docker-запуска не требуются.

1. Выбрать компанию «Ромашка» и расчётный счёт. В источнике1131операция C001;
   два ручных будущих плана добавлены smoke-проверкой и являются тестовыми.
2. Раскрыть «История расчётов», нажать «Открыть». Появятся сохранённый график,
   объяснения и дневные значения. Открытие не создаёт новое задание.
3. Для нового расчёта выбрать срез и нажать «Рассчитать». У C001 фактическая
   последняя операция2026-09-29; прежняя ручная приёмка2026-09-30 хранится отдельно.
4. Для повторного импорта выбрать ту же `statements/C001.csv` из переданного ZIP,
   проверить и подтвердить. Операции сохраняют те же UUID, прогноз обновляется сам.
   Подтверждение показывает сохранённую сводку импорта, а не число новых вставок
   при каждом запросе. Сводный `all_operations.csv` содержит несколько компаний.
5. Добавить будущий платёж или загрузить CSV обязательств. В таблице видны
   источник, статус и остаток; после сохранения/отмены график обновляется.
6. В «Сверка плана и факта» посмотреть связанные оплаты. Неоднозначные предложения
   раскрывают реквизиты; можно подтвердить всю или часть доступной суммы. Источники
   и бюджеты перепроверяются сервером, повтор не дублирует оплату.
7. На готовом базовом прогнозе выбрать один из четырёх сценариев. Задержка и рост
   регулярного списания требуют подходящей цели из сохранённой базы; при отсутствии
   цели UI это объясняет. Дополнительный расход показывает дневное сравнение с базой.

При сохранении новых данных через кабинет срез для планов/сверки переключается
на сегодняUTC. Смена даты, открытие истории и reload сами расчёт не запускают.

## Переделывать фронтенд

Сначала прочитать [frontend-handoff](../specs/frontend-handoff.md) и
[OpenAPI](../specs/openapi.json). Типы/клиент — `frontend/src/shared/api.ts`,
вход/выход и выбор компании — `frontend/src/App.tsx`, основные процессы —
`frontend/src/features/`. API работает под `/api/v1` на том же origin.

При изменении оформления сохранить:

- HttpOnly-сессию, CSRF-заголовок и очистку query-cache при выходе/смене пользователя.
- `CompanyPermission`: owner определяется для выбранной компании, viewer читает
  историю/данные без изменяющих действий. Без provider/при неизвестной роли запись закрыта.
- Сброс локального состояния при смене компании/счёта, async job→результат и остановку
  polling после terminal status. Возврат прежнего failedjobID при явном recovery требует
  invalidation старого кэша.
- Один автоматический POST после успешной записи, отсутствие POST при history/reload,
  сохранение старых frozen результатов. Смена даты убирает прежний график до расчёта.
- Русские подписи источников/ограничений. Недоступную вероятность не превращать в0%.
- Раскрытие реквизитов доступно во время refetch; денежное подтверждение заблокировано
  во время обновления/записи. Не возвращать потерю pointerclick из A30.
- Деньги в API — целые копейки; перевод в рубли только для отображения/ввода.

Для разработки и тестов — команды README. CI этой ночью мог не запуститься по
согласованному решению о квоте; реальные падения локальных тестов исправлять.
Синтетические Chromium E2E лежат в `frontend/e2e`, проверки компонентов —
`frontend/tests`. Селекторы основаны на доступных названиях и устойчивых UUID.

## Что проверено и что остаётся

Серверный код совпадает с A27:429Linuxтестов; последний полный Windows414/A25 и23
профильныхA27. A30:13unit/9Chromium и10повторов ручной сверки. A31:профильныйworkflow,
lint/TypeScript/Dockerbuild. Точные версии/время и независимые reviewtrees —
[requirements](REQUIREMENTS.md) и [расширенное ревью](reviews/20261024-expanded.md).

На текущем C001 пройдены реальный браузер и сохранность прежних результатов.
Свежий dump восстановлен в отдельную пустуюБД:1131UUID/13полныхForecastOut/2плана
совпали; очередь копии реально прошла pending→worker→success. Детали и SHA —
[A32-RESTORE-CURRENT](A32-RESTORE-CURRENT.md). Production/HA/перезагрузка Windows
этой проверкой не подтверждались.

Ограничения, которые нужно учитывать при демонстрации и планировании:

- Точность вероятности нового разрыва не подтверждена: новый default2.0 возвращает
  `None`. Дата/дефицит по медиане, график и источники работают. Диапазон не гарантия.
- Подключение банков/1С и самостоятельный расчёт налогов не реализованы; обязательства
  вводятся вручную/CSV с известными суммами, датами и происхождением.
- Исторический план-факт ограничен без полного версионирования документов. Полного
  инкрементального пересчёта нет; изменение внешним APIклиентом требует явного прогноза.
- F2: поменять mapping уже загруженного failedpreview с теми же байтами пока нельзя.
  Несовместимая миграция не выполнялась. Одинаковые no-ID операции неразличимы.
- Расширенные B7/B8matcher/B9/B10 не объявлены готовыми. Их качество и новые метрики
  требуют отдельной работы; отсутствие опубликованного heartbeat не доказывает,
  что процесс агента на чужом компьютере остановлен.

## Стенды и возврат агента B

Текущие адреса на ПК владельца:18086 — исходный C001,18087 — синтетические E2E,
18089 — изолированная проверка ролей,18090 — восстановленная копия с дополнительным

pytest запускается только на отдельной БД с суффиксом `_test`; fixtures очищают её.

B при возвращении сначала читает удалённые A.md/архив/решения/fallback, сохраняет
свой WIP и публикует RETURN. Затем явный HANDOFF/ACK по PROTOCOL§7. Его ветку не
переписывали. Новый фронтенд и аналитические изменения вести отдельными согласованными
пакетами от проверенной общей базы. Main одобряет и сливает человек.
