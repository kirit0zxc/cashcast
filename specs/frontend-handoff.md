# Утренний frontend: подключение к настоящему CashCast

Это описание уже реализованных ручек, а не новый контракт. Машинные типы и поля:
[openapi.json](openapi.json), бизнес-правила [api.md](api.md). Точный проверенный SHA,
активная версия модели и стенд — README и описание проверяемого PR.
Изменения оформления можно делать отдельно, сохраняя эти правила интеграции.

## Запуск и сессия

Один Compose по README поднимает nginx/web, FastAPI, worker и PostgreSQL. Браузер
обращается к `/api/v1` на том же origin; отдельный публичный адрес БД не нужен.
Локальный демо-вход указан в README. Для редизайна: Node24, `npm ci`/`npm run dev`
из frontend. Vite слушает127.0.0.1:5174 и проксирует `/api` на127.0.0.1:8080.
Для текущего стенда владельца перед запуском задать в PowerShell
`$env:CC_DEV_API_TARGET='http://127.0.0.1:18086'`.
На Linux/macOS: `CC_DEV_API_TARGET=http://127.0.0.1:18086 npm run dev`.
При занятом5174 запуск останавливается, порт не меняется сам. API/worker/БД должны
уже работать в Compose; dev-сервер не запускает их. Готовый Docker-стенд не требует
Node/Python на компьютере пользователя. Порты соседнего HoneyForge5173/8000 не трогать.
Контроллер прогноза живёт в AccountProvider выше страниц. Автоматический POST
отправляется только обработчиком успешной записи, не mount-effect страницы.
Переходы по меню и StrictMode не создают задания. Контроллер сохраняет job между
вкладками; sequence отбрасывает запоздалый ответ прежнего запроса.

## Разделы и общее состояние

Маршруты: /overview, /operations, /import, /payments, /reconciliation, /forecast,
/scenarios, /pulse и отдельный /assistant. nginx и Vite обслуживают прямые адреса;
Back/Forward меняют страницу без сброса контекста выбранного счёта. Компания/счёт
общие для разделов; их смена перемонтирует AccountProvider и очищает чат/выбор.
История чата сохраняется только при переходах внутри текущего счёта, не после reload.

Обзор читает последнюю успешную базу из всей истории с пагинацией, пропуская
сценарии и незавершённые/ошибочные задания. Пустая история имеет явную подсказку,
а disabled query не считается вечной загрузкой. Сверка обновляет собственный
результат сразу после commit, независимо от успеха последующего forecast enqueue.
Unknown в «Пульсе» означает отсутствие оценки, не сохранность подушки.
Подтверждения ассистента идут через action_id; propose_forecast открывает уже
созданное задание без второго POST, остальные записи помечают прогноз устаревшим.

1. `POST /auth/login` с `{email,password}` ставит HttpOnly `cc_session` и доступную
   JavaScript cookie `cc_csrf` (без HttpOnly), возвращает
   `{id,email,csrf_token,companies:[{id,name,role}]}`.
2. После reload `GET /auth/me` восстанавливает пользователя/компании/CSRF.
3. POST/PATCH передают `X-CSRF-Token` из ответа и cookies, `credentials:same-origin`.
   Для multipart не задавать Content-Type вручную: браузеру нужен boundary.
4. `POST /auth/logout` →204 без JSON. После смены пользователя очищать query-cache
   и локальное состояние всех компаний/счетов. Токены не писать в localStorage/логи.

401 — сессии нет/истекла, 403csrf_failed — неверный CSRF, чужая сущность404.
Общая ошибка `{error:{code,message,field_errors,request_id}}`; тело ошибки не `detail`.
UI должен показывать сообщение и возможность исправить ввод/войти повторно.

Роль из MeResponse относится к каждой компании отдельно. Owner изменяет её данные;
viewer читает сохранённые данные/историю, но получает403read_only_company для всех
изменяющих ручек, в том числе preview/forecast/scenario и UUID-object commit/PATCH.
Минимальный кабинет уже скрывает изменяющие действия viewer: импорт/категории/планы/
сверка/новый прогноз/новый сценарий. История, просмотр графика/причин, списки и выход
доступны. CompanyPermission берёт роль именно выбранной компании из me; без provider
или при неизвестной роли запись закрыта. Автоматический forecastPOST также требует owner.
Это удобство UI, сервер остаётся окончательной проверкой прав (в том числе при отзыве).
При утреннем редизайне сохранить этот provider и guards, не открывать actions по
одной лишь роли пользователя в другой компании. Новых user/role API не добавлено.
Управления ролями в этом API нет. Отсутствие членства остаётся404.

## Счёт и импорт

Commit идемпотентен: повтор возвращает сохранённую исходную сводку, не delta новых
вставок текущего запроса. UI подписывает результат соответствующим образом. Сам факт
preview.reused означает прежнюю загрузку файла и не гарантирует, что он уже committed.
После успеха новый UIпрогноз использует фактический preview.period_end: у C001 это
2026-09-29, календарный срез 2026-09-30 выбирается отдельно.

`GET /companies/{company}/accounts` →`{items:[{id,company_id,name,currency}]}`.
UUID счёта обязателен для выписки/прогноза; нельзя подменять его названием/индексом.
При смене компании/счёта сбрасывать preview, курсоры, job и выбранный прогноз.

`GET /import-presets` отдаёт participants-v1: UTF-8 BOM, `;`, русские направления,
ИНН как строка. Пользователь выбирает одну `statements/Cxxx.csv`. Сводный файл с
теми же операциями нельзя добавлять как ещё один независимый источник.

`POST /companies/{company}/imports`: multipart `account_id`, `file`, `mapping`
(JSON-строка объекта пресета). Preview содержит import_id/status/total_rows/error_count/
sample_errors/period_start/period_end/reused. Кнопка commit недоступна при errors.
`POST /imports/{id}/commit` →статистика inserted/skipped_existing. Повтор возвращает
первоначальную статистику, а не число новых строк этого HTTP-запроса.

Известный незакрытый дефект: исправленный mapping тех же байтов после failedpreview
пока возвращает старый import. Решение statement-mapping-v1 предложено A020, ACK и
реализация ожидаются. Не обходить это изменением байтов/ID на фронтенде.

Счета/обязательства — отдельный поток: `POST /companies/{company}/obligation-imports`
с file/account_id/source_name/as_of; после preview без ошибок —
`POST /obligation-imports/{id}/commit`. Шаблон: evaluation/examples/obligations-demo.csv.
Конфликт изменённого sourceID409SOURCE_ID_CONFLICT откатывает весь набор.
Источник/provenance/tax_regime — данные документа, не подтверждение налоговой проверки.

## Данные и план-факт

`GET /companies/{company}/transactions?account_id=...&limit=25&cursor=...`
→`{items,next_cursor}`. Курсор непрозрачный, следующая страница использует его целиком.
`PATCH /transactions/{id}/category` принимает значение Category из OpenAPI; ручная
категория сохраняется при повторном импорте/автокатегоризации.

`GET/POST /companies/{company}/planned-events` — список/новый план; PATCH по
`/planned-events/{id}` меняет дату, сумму или статус. Список компании содержит разные
счета: отображать только выбранный account_id. В UI уже есть создание/CSV/отмена.
У плана показывать исходную сумму, remaining_amount_minor, статус и источник.
Отмена не удаляет документ и не возрождается при идентичном CSV-reimport.

`GET /companies/{company}/plan-fact?account_id=...&as_of=YYYY-MM-DD` только читает:
items[{event,confirmed_amount_minor}], confirmed_matches и proposals. Proposal может
быть альтернативой другому, суммы альтернатив нельзя складывать и считать оплатой.
`POST` на тот же URL применяет только безопасные auto-confirm на сегодняUTC.
Минимальный UI уже показывает связанные суммы, остатки, просрочку, предложения и
подтверждённые связи; отдельная кнопка вызывает этот безопасный POST.
Ручное подтверждение: `POST /companies/{company}/plan-fact/confirm` с body
`{account_id,planned_event_id,transaction_id,matched_amount_minor}`. UUID обязательны,
сумма — строгий integer1..9e15копеек; лишние поля/as_of отклоняются. Только сегодняUTC,
session/CSRF. Сервер заново проверяет текущий matcher proposal и оба денежных бюджета.
Одинаковая confirmed пара/сумма200, другая сумма409allocation_conflict;
отсутствующий/устаревший proposal409proposal_stale, чужой объект404. Ответ PlanFactOut.
После ошибки обновить список, после успеха — планы/план-факт и запросить новый
forecast на сегодняUTC. Минимальный UI показывает банковские реквизиты до подтверждения,
позволяет частичную сумму. Legacy candidate/rejected не перезаписываются молча409.
Раскрытие реквизитов — чтение: не отключать кнопку из-за фонового refetch план-факта.
Иначе смена disabled во время pointerdown/up может потерять клик. Денежные поля и
подтверждение, напротив, блокируются во время refetch/записи; сервер всё равно заново
проверяет proposal и бюджеты. При изменении суммы/пары карточка пересоздаётся намеренно.
Основание — F4 временного fallback-решения0082ec3, не ACK B.

Paid/cancelled нельзя возобновить или менять их сумму:409closed_plan_event; повтор
той же суммы/статуса200. Правка активной суммы до оплаченной закрывает план вpaid.
Противоречащий остатку активный status422invalid_plan_status. При
422plan_fact_resource_limit показать ошибку, не считать отсутствие ответа пустой
сверкой: допустимо не более100000пар активных планов и доступных операций.
Предупреждение «расчётный остаток» означает EOD плюс известные последующие факты,
а не новый банковский остаток. Не скрывать исходную дату подтверждённого EOD.

Историческое состояние планов ещё не версионируется полностью. Сервер может вернуть
409historical_plan_unavailable; POST historical reconcile запрещён. Сегодняшний ввод
плана не должен незаметно становиться известным в старом прогнозе.

## Прогноз и четыре сценария

`POST /companies/{company}/forecasts` с account_id/as_of/horizon_days(1–180)/seed?
→202 `{job_id,forecast_run_id,status}`. Затем опрос `/jobs/{job_id}` до succeeded/failed.
При failed показывать error_code; не опрашивать бесконечно. После succeeded читать
`GET /forecasts/{forecast_run_id}` и `/explanations`. Ответ фиксируется до отправки202;
немедленный GET не должен требовать маскирующий404 retry.

После известного временного сбоя и исчерпания попыток owner может повторить исходный
POST: вернутся те же ID, pending и новый boundedбюджет3. Старый закэшированный failedjob
следует refetch, даже если job_id совпал. Ни постоянные/неизвестные ошибки, ни legacy
без snapshot этим не возобновляются. Автоматически повторять terminalfailed в цикле
нельзя; это явное действие пользователя. При изменившемся входе/активной версии
модели обычный новый запрос может создать отдельный run, старый сохранится.

Forecast — сохранённый снимок с model_version/data_version/seed, points и risk.
Идентичный запрос возвращает прежний run, изменившийся вход — новый.
`GET /companies/{company}/forecasts?account_id=UUID&limit=20&cursor=...` возвращает
`{items,next_cursor}`; limit1–100, порядок created_at/id DESC. Items содержат
id/account_id/as_of/horizon_days/status/model_version/data_version/seed/
base_forecast_id/created_at/error_code/job_id. Legacy job_id nullable. Курсор
связан с компанией и счётом; неверный/чужой422invalid_cursor, чужой ресурс404.
Никаких raw snapshots в истории; GET не создаёт задания. Временное согласование
forecast-history-v1 — fallback-a-20261024T0114Z-v1, это не ACK B.
Prototype открывает сохранённые base/scenario после reload, показывает пагинацию
по10 и ожидает worker только при существующем job. Legacy pending без job остаётся
информационным состоянием, без автоматического повторного запуска. Для сценария
доступен переход к его сохранённой базе; вложенный scenario UI не предлагает.

Сценарий: `POST /forecasts/{baseId}/scenarios` с `{changes:[...]}` →такой же asyncflow.
Четыре вида: add_expense(amount_minor,on_date), delay_event(target_id,shift_days),
reduce_irregular_inflow(factor0…1), increase_recurring(target_id?,factor1…2).
Проценты в UI переводятся в factor; money — в целые копейки до отправки.
Цели принадлежат frozenbase: prototype берёт planned-in и recurrence-out из её
explanations/source_ref/detail, а не из сегодняшнего списка изменённых планов.
Если подходящей цели нет, объяснить это и предложить новую базу; не придумывать ID.

`GET /forecasts/{scenarioId}/comparison` отдаёт base/scenario p50 и delta по дням,
оба risk. База неизменна; scenario не записывает реальные оплаты. Вложенный scenario
и сравнение разных seed/моделей/входов дают409. После изменения формы убирать старое
сравнение, на время задания блокировать повторную отправку. Все4формы уже работают.

## Как честно показывать числа

В таблице операций уже есть ручная категория через существующий
`PATCH /transactions/{id}/category` с `{category: <Category enum>}`. Серверный
category_source отличает manual от auto; ручной выбор сохраняется при reimport.
Редактор обновляет список операций, но не переписывает сохранённый forecast.
Изменение учитывает следующий расчёт; не показывать ручную confidence=1 как accuracy.

## Автоматический запрос после успешной записи

В минимальном кабинете successful statementcommit/obligationcommit/create/cancel/
reconcile/manualconfirm/category вызывает обычный POSTforecast и ожидает job.
Импорт выбирает period_end, планы/сверка — todayUTC, категория сохраняет выбранный
пользователем срез. Account/company/user смена отделяет локальное состояние.
Общий контроллер получает callback успешной записи независимо от открытой страницы.
Invalidation GET и обновления job/history сами callback не вызывают.
История/reload/смена даты/переходы между разделами POST не создают.
Смена даты очищает прежний график до явного расчёта; открытие historyentry выставляет
её as_of. На todayUTC существующий POSTforecast также применяет safeauto-reconcile,
поэтому однозначная оплата может быть записана сразу после успешной загрузки/плана.
Это явно подписано в кабинете; неоднозначные оплаты остаются ручными. Для тестовой
неоднозначности несколько документов должны существовать атомарно до первого POST.
Редактирование категории обновляет список операций. Курсоры принадлежат странице
операций; смена раздела/счёта сбрасывает её локальные фильтры и позицию.

Новый результат не переписывает сохранённый, а открывается отдельно; пока worker
работает, старый график не выдаётся за пересчитанный. Terminalfailed показывает
ошибку/ручной повтор, а не запускает цикл. Сценарий остаётся отдельным явным действием.
Это интеграция данного кабинета, не серверная подписка на изменения других клиентов
и не инкрементальная математика. Сохрани этот поток после визуального редизайна.

Все *_minor — целые копейки, RUB; форматировать через shared/money.ts. Number/100
может терять копейку на верхней границе, formatter использует BigInt и проверяет safeint.
Неизвестная сумма/вероятность отличается от нуля. Probability null →«недоступна»,
0 →0%. risk.available=false не обнуляет существующие p50-даты/дефицит.

В текущем default seasonal-guarded-2.0-w84 вероятность нового разрыва не подтверждена
и скрыта(None). F5 активирует уже зарегистрированную модель, без новых параметров;
старые1.0 snapshots/jobs/scenarios сохраняют свою версию. p10/p90 — эмпирические
траектории модели, при плохих данных схлопываются кp50, не банковская гарантия.
Допущения/data_warnings и provenance должны оставаться видимыми после редизайна.

## Что сохраняют тесты

`npm run test:unit` на Node24 проверяет денежные границы. Chromium E2E на отдельном
Compose проверяют вход/ошибку пароля/CSV/прогноз/выход, планы/CSV/cancel/reimport и
четыре численных сценария/immutablebase. Эти сценарии нужно сохранить при редизайне.
Это интеграционные проверки, не оценка качества модели на настоящих банковских данных.
