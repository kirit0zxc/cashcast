# Кассовые разрывы v1

Владелец 24.10.2026 поручил завершить карточку разрыва, причины и проверку действий
отдельным PR. Дополнение к существующему API; старые прогнозы и DTO не меняются.

## Контракт

- `GET /api/v1/forecasts/{id}/cash-gaps` — карточка по сохранённому успешному расчёту.
- `POST /api/v1/forecasts/{id}/cash-gap-preview` — `{actions: [...]}`, 1–3 действия.
  Только вычисление ответа, без записи, задания и изменения планов. Owner/viewer
  своей компании, CSRF на POST. Чужой прогноз — 404, неготовый/неполный — 409.
- `delay`: `flow_id` из карточки, `to_date`, `payment_delay_agreed` для расхода.
  Перенос поступления — стресс, перенести расход можно только для закупки.
  Налог, зарплата, аренда, кредит и неклассифицированный расход защищены.
  Новая дата строго позже исходной и внутри горизонта. Один поток — один перенос.
- `financing`: `date`, `amount_minor`, `repayment_date`, `cost_minor`.
  Получение после as_of внутри горизонта, возврат позже получения. Стоимость —
  заданная пользователем полная сумма, не ставка/предложение банка. Возврат включает
  тело и стоимость; долг после горизонта явно возвращается отдельным полем.
- Деньги — целые копейки. OpenAPI: `CashGapOut`, `CashGapPreview`.

Согласованное дополнение входного DTO: `PlannedEventDTO.category: str | None = None`.
Категория копируется из плана при создании снимка и участвует в data_version;
старые снимки без поля читаются как неизвестная категория и не получают право
переноса. Тип плана `kind` не является категорией; `kind=tax` защищён даже при
противоречивой категории purchases. Миграция БД не требуется.

## Семантика

Точки: as_of (начальный остаток) плюс все сохранённые дневные p50. Разрыв —
непрерывный интервал отрицательных остатков на конец дня. Ноль означает восстановление.
`existing` начинается на as_of: настоящее начало неизвестно. `new` начинается позже,
в том числе после восстановления существующего дефицита. `observed_days` считает
отрицательные дни включая дату среза; день восстановления не включён.
`duration_is_lower_bound` при existing и/или отсутствии восстановления до конца ряда.
`max_deficit_minor` и `total_negative_days` включают открывающий остаток.
`days_until_new_gap` — число календарных дней от as_of до первого нового разрыва,
либо null. `required_reserve_minor` — минимальная постоянная добавка к начальному
остатку, которая делает все точки данного ряда неотрицательными. Это тот же максимум
дефицита, выраженный как потребность в резерве; не кредит и не гарантия модели.
Резерв нужен с начала ряда, при existing — уже на as_of. Долг с возвратом оценивается
только через financing preview. Ноль при insufficient_data не подтверждает безопасность.
Из-за этого финансирование завтра не устраняет уже существовавший сегодня дефицит.

`status=no_gap` лишь при пригодной истории и отсутствии отрицательных точек.
Иначе без минуса — `insufficient_data`; при минусе — `gap` с предупреждением качества.
`causes` — знаковое разложение исходного минимума: начальный остаток + планы +
оценочные потоки + поправка к медиане. Сумма точно равна `causes_balance_minor`.
Это состав расчёта, не утверждение причинности; планы не выдаются за оплаты,
регулярности — оценка. Идентификаторы источников относятся к frozen-снимку.

В preview base неизменна, preview — сдвиги детерминированной медианы; это не новая
обученная модель и не пересчёт вероятности. `improvement_minor` может быть отрицательным.
Не обещаем устранить дефицит после конца горизонта. Просмотр не требует подтверждения
изменений, потому что никаких изменений не выполняется.

## Вероятность и проверка качества

Новые расчёты2.1 показывают модельную вероятность минуса со статусом
`estimated_uncalibrated`; см. [политику2.1](estimated-probability.md). Preview медианы
не выдаёт старую вероятность за новую после изменения действий.
Для старых расчётов2.0 сохранена политика B6: `probability=null`, `probability_status=unavailable`, причина
явная. В `evaluation/B6-REPORT.md` и `calibration-v2.json` уже есть сравнение raw,
constant, logit-intercept и monotone-PAVA. Проверка новых разрывов дала лишь четыре
test-fold у трёх компаний, precision 11.1%, recall 50%; это недостаточная основа для
числовой вероятности в продукте. Не заменяем эту проверку точностью на синтетическом
smoke. Повторное открытие числовой оценки требует новой независимой временной проверки.

## Интеграция UI

`CashGapPanel` внутри успешного ForecastPanel, key=forecast ID. Показывает эпизоды,
разложение, график base/preview и формы действий. Не меняет общий layout Дианы.
Для будущей вкладки достаточно перенести компонент, сохранив api и forecastId.
После новых операций нужно выбрать новый успешный прогноз; старый отчёт неизменен.
