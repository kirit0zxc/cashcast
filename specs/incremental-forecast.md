# Инкрементальное обновление фактов и планов v2

Владелец 24.10.2026 прямо расширил задачу: обновлять прогноз при загрузке новых
фактических операций без полного расчёта. Это оптимизация исполнения
seasonal-guarded-2.0-w84, а не новая обученная модель. v2 заменяет границы v1.

## Поддерживаемые изменения

Новые и запоздалые операции, исправление/удаление факта, категории, подтверждённого
остатка, движение as_of вперёд и изменения планов. Импорт сохраняет прежние правила
идемпотентности: конфликтующий внешний ID не является разрешением перезаписать факт.

Worker:
1. Сравнивает подписи операций по ID, категоризирует только изменённые.
2. Пересчитывает затронутые старые/новые группы регулярности. При смене as_of
   проверяет все группы: регулярность может истечь. Для этого хранится вся история,
   не только 84-дневное статистическое окно.
3. Обновляет исключения регулярных операций, включая старые даты затронутой группы.
   Вычитает прежние вклады и добавляет новые в дневные остаточные суммы.
4. Формирует окно до 84 календарных дней с нулевыми днями; обновляет средние по
   дням недели и прежние условия достаточности истории.
5. Переиспользует сетку выборки bootstrap при тех же упорядоченных допустимых
   стартах блоков/seed/horizon. Если состав выборки меняется, генерирует её заново.
   К каждой траектории применяет накопленную разницу выбранных дневных потоков
   и изменение начального остатка.
6. Пересчитывает календарное сопоставление целиком: неоднозначность зависит от
   других платежей. Добавляет накопленные плановые потоки к остаточным траекториям.
7. Заново считает квантили, риски, объяснения и компоненты. Уже округлённые
   квантили не сдвигаются: сохраняется прежнее округление половины копейки.

Все продуктовые результаты должны совпадать с независимой замороженной моделью
при одинаковом входе. API build_snapshot по-прежнему читает, подготавливает и
валидирует полный снимок, включая категоризацию/регулярности этой подготовки.
Оптимизация относится к вычислительному состоянию worker; весь запрос не объявляется O(delta).

## Хранение и fallback

Закрытое состояние ledger-update-v2 находится в ForecastRun.details._incremental_state,
сохраняется одной транзакцией с результатом, проверяется checksum. API его не отдаёт.
Кандидаты: последние 8 успешных базовых запусков той же компании, счёта, модели,
seed и горизонта с as_of <= новой даты. Старые снимки/результаты неизменны.

Полный расчёт: первый запуск; отсутствие, повреждение или старая версия checkpoint;
другая модель, seed, горизонт; сценарий; движение даты назад без совместимого более
раннего checkpoint. Старые v1 состояния требуют первого полного расчёта.
Идентичный повтор возвращает прежний run — это идемпотентность, не incremental.
Состояние переживает перезапуск worker. Лимиты вычислений и проверки денег сохраняются.

## Публичная диагностика

GET /api/v1/forecasts/{id}, nullable calculation, пример:

```json
{
  "mode": "incremental",
  "reason": "observed_data_changed",
  "reused_history": true,
  "bootstrap_paths_generated": 0,
  "source_forecast_id": "uuid",
  "categorized_transactions": 2,
  "reused_transactions": 168,
  "recurrence_buckets_recomputed": 2,
  "daily_aggregates_changed": 1,
  "trajectory_values_updated": 6000
}
```

Числа иллюстративны. reason=planned_events_changed при изменении только планов.
daily_aggregates_changed считает затронутые даты, даже если итоговая разница нулевая.
При изменении окна/достаточности истории частичный расчёт может построить 200 новых
траекторий. Ноль траекторий сам по себе тоже не доказывает incremental.
Проверять mode, source_forecast_id и счётчики вместе. Для старых запусков поля nullable.
UI показывает режим/источник/счётчики. Вероятность разрыва остаётся unavailable.

## Проверки

- Независимая legacy-модель: append/late/edit/delete/category/direction/date,
  возникновение/разделение/истечение регулярностей, смена окна и as_of,
  reconciliation break/repair, горизонты 1–180 дней, JSON roundtrip.
- В неизменённом окне запрещён повторный RNG; категоризация только новых операций.
- PostgreSQL: реальный CSV сегодня после вчерашнего среза, сохранение источника,
  изоляция компаний/счетов, повтор импорта без дублей и неизменность старого run.
- UI без моков: импорт выписки -> автоматический новый incremental forecast.
- Повреждённое состояние, включая context=null, безопасно ведёт к full.

Пошагово: [инструкция](../docs/check-incremental-forecast.md).
