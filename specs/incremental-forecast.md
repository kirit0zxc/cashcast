# Частичное обновление календаря v1

Запрос владельца 24.10.2026: реализовать обновление без полного пересчёта и дать
инструкцию проверки. Реализация в отдельной ветке от main, с человеческим merge.
Это оптимизация исполнения существующей модели 2.0, не новая обученная модель.

## Границы

При изменении плановых событий (ввод/импорт, сумма, дата, направление, оплата,
отмена) worker переиспользует категории исторических операций, найденные
регулярности, средние по дням недели и 200 ранее сгенерированных траекторий.
Пересчитываются календарь с подавлением двойного счёта, остатки/квантили,
источники риска, объяснения и компоненты. Все продуктовые результаты совпадают
с полным расчётом при том же входе. Валидация входа, quality и сбор снимка в API
сохраняются: чтение/проверка истории и подготовка DTO не объявляются инкрементальными.

Новая/исправленная фактическая выписка, остаток, дата среза, seed, горизонт,
сценарий, модель или отсутствие совместимого checkpoint требуют полного расчёта.
Это **не online-обучение на новых банковских транзакциях**. Старые сохранённые
прогнозы до внедрения не имеют checkpoint; первая новая версия считается целиком.
Повтор идентичного запроса возвращает прежний run; это не отдельный частичный расчёт.

## Хранение и выбор

Без миграции: закрытое состояние в `ForecastRun.details._incremental_state`,
в одной транзакции с успешным результатом worker. Version `calendar-update-v1`,
SHA-256 канонического входа без planned_events/data_version, checksum состояния.
Выбор только среди последних 8 успешных базовых запусков того же tenant/account,
модели, даты, горизонта и seed. Нет межсчётного/process-global cache.
Состояние переживает перезапуск worker. Старый снимок и его результат неизменяемы.

Исторические траектории хранятся без вкладов планов. К новому результату добавляется
новый накопленный календарный поток в целых копейках; квантили округляются заново
по прежнему алгоритму. Сдвиг уже округлённых квантилей не используется, чтобы
не менять округление половины копейки. Короткая история сохраняет deterministic fallback.
Ресурсные ограничения на число планов/стоимость сопоставления и выходные деньги
действуют для обоих режимов. Повреждённый checksum/старая версия -> полный расчёт.

## Дополнение публичного ответа

Существующий `GET /api/v1/forecasts/{id}` дополнен nullable `calculation`:

```json
{
  "mode": "incremental",
  "reason": "planned_events_changed",
  "reused_history": true,
  "bootstrap_paths_generated": 0,
  "source_forecast_id": "uuid-предыдущего-прогноза"
}
```

`mode=full`, `reason=no_compatible_checkpoint` — совместимого состояния нет;
`scenario_requires_full` — сценарный расчёт. Для старых/неподдерживаемых моделей
и незавершённых запусков поле может быть `null`. `bootstrap_paths_generated=0`
само по себе не доказывает incremental: так бывает при короткой истории.
Клиент проверяет mode, reused_history и source_forecast_id вместе.
Внутренний checkpoint, сырая история и значения симуляций в API не возвращаются.
UI показывает режим и источник в подробностях. Вероятность разрыва остаётся unavailable.

## Приёмка

- Добавление/перенос/оплата/отмена/смена направления, короткая и достаточная история,
  JSON roundtrip: продуктовые поля равны full до копейки.
- Запрет вызовов RNG, подготовки истории и детектора в частичном model run.
- PostgreSQL/новый Session: новый план -> новый run incremental; старый ответ неизменен.
- Изменение факта, seed/date/horizon/account/scenario -> full; испорченное состояние -> full.
- Реальный UI без моков: полный расчёт, новый расход, частичный расчёт, отмена.

Пошаговая проверка: [инструкция](../docs/check-incremental-forecast.md).
