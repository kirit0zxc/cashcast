# Проверка контрольного датасета v1

24.10.2026 владелец поручил Данилу импорт/проверку файла, нам — пункты 2–5:
временной backtest, метрики, журнал, графики и выгрузку. Это реализация оценки
действующей модели, не новый эксперимент обучения или подбор параметров.

## Граница с Данилом

Используем существующие Account, BankTransaction, DailyBalance и импорт API.
Данил сохраняет операции и подтверждённые дневные остатки, возвращает company_id,
account_id, период покрытия и SHA-256 исходного файла. Один счёт — одна валюта RUB.
Операции направлены in/out, amount_minor — положительные целые копейки; остаток
closing_balance_minor — целые копейки, допускает минус. Не дублировать EOD внутри дня.
Пропуск дня не превращать в нулевой остаток. Другие валюты нельзя переименовывать в RUB.
Несколько компаний импортируются раздельно, проверка v1 запускается по одному счёту.

POST /api/v1/companies/{company_id}/evaluations:
account_id, as_of (первая дата среза), horizon_days (1–90), folds (1–12),
threshold (0–1, default 0.5), seed (default 42), complete_statement (default false),
source_sha256 (необязательный SHA-256, предоставленный импортёром, а не проверенный
повторно этим API). Результат 202: id, status. Проверки идут последовательно с шагом
horizon_days; обучение каждого среза содержит только историю <= as_of этого среза.
Последний горизонт не позже текущей даты UTC. Настройки фиксируются ДО расчёта.

GET /api/v1/evaluations/{id} — статус и неизменяемый результат в Job.result.
GET /api/v1/companies/{company_id}/evaluations?account_id=... — последние 20 проверок
счёта, только ID/статус/код ошибки, без больших отчётов и исходного снимка.
GET /api/v1/evaluations/{id}/report?format=json|html — скачать отчёт после завершения.
POST требует owner и CSRF; GET доступен только участникам компании.
Новая миграция не нужна: стандартная очередь, payload и result существующей Job.
Повтор одинакового frozen-снимка/параметров дедуплицируется. Изменение данных даёт новый ID.
Worker имеет три попытки. Явный повтор POST для исчерпавшего попытки failed-задания
возобновляет тот же снимок под блокировкой строки; успешный результат не меняется.

## Честность проверки

На enqueue сохраняем ограниченный снимок операций/остатков; worker не читает живую
выписку. Вход модели каждого окна физически отделён от будущего факта. Категории
пересчитываем только по прошлым операциям. Используем get_forecast_service(default),
закрепив версию при постановке. Плановые события исключены из statement-only backtest:
в БД нет полной истории изменений статуса обязательств. Не выдавать его за оценку
сценариев с планами. В журнале явно отражаем это ограничение.

Нужен наблюдаемый EOD точно на дату среза. Иначе окно пропускается с причиной.
complete_statement=true означает явное подтверждение пользователя/импортёра, что
потоки на тестовом интервале полны. Только тогда отсутствие операции = нулевой поток,
а пропущенные EOD можно восстановить по opening + cumulative(in-out). Любая несверка
с наблюдаемым EOD запрещает восстановление и оценку потоков этого окна.
Без подтверждения оцениваем остаток только на наблюдаемых датах; неизвестность не
заполняется нулём. Матрица горизонта требует факта каждого дня и opening >= 0.

MAE/MSE/RMSE считаются отдельно по остатку/поступлениям/списаниям в RUB/RUB².
Матрицы: ежедневный минус по медиане; ежедневный минус по probability>=threshold;
новый минус за горизонт по probability_any_negative>=threshold. Не смешиваем единицы
наблюдения. Accuracy/precision/recall/F1, Brier, ROC-AUC, AP; неопределённые значения
null с причиной, никакого NaN. ROC-AUC требует оба класса, AP — положительные примеры.
Покрытие p10–p90 — эмпирическое; вероятность модели некалибрована. Порог не подбираем
на контрольном файле. Статистической независимости дней/окон одного счёта не обещаем.

В отчёте: хэш нормализованного frozen-набора, версия, seed, даты, число строк,
пропущенные окна, шаги расчёта и дневные агрегаты. Ни назначений, ни имён контрагентов,
ни исходных строк в отчёте/серверных логах. HTML автономен, без внешних ресурсов.

## Показ за 15 минут

0–3: импорт Данила и проверки файла. 3–5: выбрать счёт, срез/горизонт/число окон,
подтвердить полноту только если установлена. 5–10: выполнить проверку, показать
график, метрики, матрицы и журнал. 10–12: скачать JSON/HTML. 12–15: обычный прогноз
и минимальные функции демо. Если будущего факта нет, показать прогноз, а метрики
отдельно на историческом holdout; не объявлять будущую точность известной.
