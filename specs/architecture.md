# Архитектура (модульный монолит)

```
Браузер (React/TS)
      │  /api  (cookie-сессия)
      ▼
nginx  ──►  FastAPI (api)        PostgreSQL
                │  ставит job        ▲
                ▼                     │ очередь + lease
             worker  ────────────────┘
          (тот же образ, другая команда)
```

- **Один образ backend** для `api` и `worker` — разные команды запуска.
- **Очередь в PostgreSQL**: `SELECT … FOR UPDATE SKIP LOCKED` + lease/повтор. Без брокеров.
- **Локальный вход один** — `web` (nginx), bind127.0.0.1. `api`, `worker`, `postgres` во внутренней сети.
- **Снимок прогноза неизменяем**: сценарии считаются от зафиксированной базы тем же расчётом.

## Пакеты backend

```
app/core/        настройки, БД, ошибки, сессии, request_id, модели
app/modules/
  imports/       разбор CSV (настраиваемый маппинг), preview, commit
  categorization/ чистые правила категорий с объяснениями
  planning/      календарные регулярности и консервативный matcher
  forecasting/   baseline, seasonal block bootstrap и сборщик снимка
  integration/   сохранение категорий и транзакционные аллокации план-факта
  jobs/          очередь и worker
app/api/         тонкие HTTP-обработчики и Pydantic-схемы
evaluation/      воспроизводимый backtest, конфигурация, агрегированные отчёты
```

## Границы владения

| Папка | Владелец |
|---|---|
| `frontend/` | A; визуальная переработка утром |
| `backend/` (ядро, api, imports, jobs, integration, snapshot), инфра, миграции | A |
| Чистые forecasting/categorization/planning, evaluation | B на ПК Димы |

Контракт между интегратором и аналитикой — `backend/app/modules/contracts.py`
(чистые DTO, без HTTP и ORM). Изменяет A после согласования точной версии с B.

## Снимок и план-факт

API блокирует счёт, учитывает подтверждённые аллокации и фиксирует полный ForecastInput
в forecast_run.input_snapshot(JSONB). Worker декодирует его, проверяет закреплённую
model_version и сохраняет результат/точки. Ручная категория, импорт и планы используют
ту же блокировку счёта. Две операции не расходуют один и тот же денежный остаток.
Сценарий копирует базовый вход, добавляет changes и использует закреплённую модель/seed;
comparison читает оба сохранённых результата, ничего не пересчитывает и не меняет.

План-факт аналитики — чистые предложения. Запись confirmed и обновление remaining
принадлежат A в одной транзакции. Альтернативные candidate не являются оплатой.
Для прошлого доступны только данные с известной временной границей; без истории
редактирования планов неоднозначный исторический запрос возвращает409.

## Граница готовности

Реальная цепочка CSV→API→PostgreSQL→worker→UI проверяется Chromium E2E и отдельной
ручной приёмкой C001. Это не доказательство качества вероятностей: опубликованный
B4 не подтвердил калибровку риска. Новые пакеты B5–B10 принимаются отдельно после
ревью, общего тестирования и CI точного кандидата.

Обновление API-контейнера меняет его адрес. nginx1.28 использует upstream zone+resolve
и DockerDNS127.0.0.11 с valid5s, поэтому старый IP не сохраняется до ручного рестартаweb.
Контролируемая проверка в отдельном демо: адрес API сменён с172.30.0.3 на172.30.255.250,
health восстановился, IDweb-контейнера не менялся. Механизм описан в
[официальной документации nginx](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#server).
