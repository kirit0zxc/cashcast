# Прогноз и оценка качества

## B0: опорная модель

BaselineForecastService остаётся сравнительным ориентиром: сумма притока и оттока
за (as_of−7, as_of], делённая на 7 целых календарных дней. Учитывается только заданный
account_id. Будущие операции и события с available_at > as_of исключены.
События paid/cancelled и нулевой остаток не добавляются. Квантили baseline совпадают;
вероятность недоступна. Это не итоговая оценка риска.

Датасет проверяется командой из корня репозитория:

```sh
python evaluation/audit_dataset.py --zip /path/cashflow_dataset_participants.zip --output evaluation/dataset-audit.json
cd backend
python -m pytest tests/analytics tests/test_baseline.py -q
```

Аудит проверяет checksum, совпадение двух представлений операций, повторные ключи,
пустые значения, остатки внутри дня и сверку соседних наблюдаемых дней. Публикуется
только агрегированный JSON. Наблюдаемая несверка не доказывает конкретную причину
пропуска. По архиву нельзя измерить точность категорий: эталонных меток нет.

## B3: аналитический прогноз

SeasonalForecastService реализует ForecastService; фабрика get_forecast_service().
Обучение на последних 28/56/84 календарных днях (пока default84, выбор окна по validation
будет зафиксирован B4). Все операции фильтруются по account и <=as_of, RUB проверяется.
Пустые дни считаются нулевыми под допущением полноты выгрузки. Остатки сверяются только
в прошлом; статистика начинается после последней наблюдаемой несверки. Нет обучения
на справочных last_operation_date или operations_count. Внешние recurrences пересчитываются
из причинного списка операций: DTO не несёт происхождения внешней оценки.

Компоненты: среднее нерегулярного потока по дням недели, календарные регулярности,
оставшиеся суммы доступных плановых событий, отдельные изменения сценария.
Исторические устойчивые повторения исключаются из нерегулярного потока. Явное событие
заменяет соответствующую регулярность по recurrence_group либо контрагенту/направлению
и дате±3 дня при единственном совпадении. Сопоставление производится по исходной дате
до delay_event. Оплаченные/отменённые события исключены. Просроченное активное событие
переносится на завтра как допущение, не как утверждение о реальном сроке оплаты.
При неоднозначной связи события и регулярности автоматическое исключение невозможно;
пользователю следует указать recurrence_group, иначе возможен завышенный ожидаемый поток.

Риск: 200 парных bootstrap-траекторий календарных недель с тем же weekday начала,
фиксированный seed. Пары притока/оттока сохраняются; годовая сезонность, будущие сдвиги
режима, спасительные пополнения владельца отдельно не моделируются. Условные p10/p50/p90
и частоты отрицательного остатка НЕ калиброванная гарантия. Дневная вероятность отличается
от вероятности хотя бы одного минуса за горизонт. first_negative/max_deficit — по p50.
Без28 дней после несверки, свежего остатка (<=3 дней) и согласованного opening вероятность
не публикуется; план/точечный прогноз доступны. Квантили траекторий не обязаны равняться
накоплению ожидаемых inflow/outflow: среднее и медиана имеют разный смысл.

Четыре сценария: delay_event (неотрицательный сдвиг известного события),
reduce_irregular_inflow (factor0..1, только остаточный приток), add_expense
(сумма>0, дата внутри горизонта), increase_recurring (factor>=1, известная группа или все).
Исходный ForecastInput и факт не меняются. Неверный вид/сумма/цель/NaN отклоняется.
Одинаковый seed даёт парные сопоставимые симуляции базы и сценария.

Wiring-v1.1: details.summary + details.explanations содержат kind,label,amount_minor?,
source_ref?,detail:{}; без исходных назначений и контрагентов. Дополнительно JSON
содержит daily_components, recurrence_ids, history_days и paths. related_event_ids
содержит только плановые события до первого отрицательного p50, не ID регулярностей.

## B4: зафиксированный выбор и оценка

Validation завершена: окна28/56/84,4 временных среза апрель–июль2026, только строки
до31августа. По MAE выбран84; фабрика уже использует84. Сетка/модель не подбирались
по сентябрю. Сентябрьский holdout122folds, выбранная модель против baseline на тех же целях.
Воспроизводимые команды, единицы, denominators и существенные ограничения:
`evaluation/REPORT.md`, `validation.json`, `holdout.json`, `selected-config.json`.

Общий MAE дневного остатка снизился; модель вероятности хуже постоянного validation
ориентира по Brier, ложных тревог много. Это не калиброванная вероятность; precision,
recall, число положительных и доступность риска обязательно читать вместе.
Первоначальное пересечение holdout через quality-gate исправлено и раскрыто в отчёте;
повтор не назван новым нетронутым holdout. Метрики на короткой истории отдельно;
на новых компаниях отдельный split не проводился. Категории без эталонной разметки
не имеют измеренной accuracy. Последующая калибровка требует нового периода оценки.

Публичное readonly `SeasonalForecastService.model_version` включает выбранное окно,
совпадает с ForecastResult.model_version; A фиксирует его при enqueue и отвергает
несовпадение при worker/scenario (model-version-v1, ACK B-010).

## B5a: quality-v2.0 и ограничение входа

Новая политика реализована отдельно в forecasting/v2/quality.py. Исходная модель1.0
пока не изменена. validate_input возвращает новый причинный ForecastInput, не мутирует
факт; account/date фильтруются до денежной статистики. Неподдерживаемый вход вызывает
ForecastInputError(ValueError) с code invalid_forecast_input или forecast_resource_limit.
Горизонт1–180, signed64seed, RUB, неотрицательные суммы операций/событий, правильные
статусы и remaining<=amount. Ошибки не содержат назначений/контрагентов.

Пределы до сортировки/симуляции:50000операций,4000остатков,2000событий,2000регулярностей,
50scenariochanges,8M текстовых символов, суммарный денежный бюджет истории/планов9e15
копеек. Ограничиваются безопасные границы календарной арифметики. Повторные id и
неоднозначные остатки одной даты отвергаются, ИНН остаётся строкой.

assess_quality: префиксная сверка остатков (без квадратичных проходов); обучение после
последней несверки. Начальный остаток сопоставляется с последним подтверждённым плюс
известные последующие операции. Суммы не исправляются. Ненаблюдаемые календарные дни
явно считаются условно нулевыми, не объявляются доказанно полными.
Режимы plan_only/point_only/empirical; интервалы симуляции требуют28пригодных дней,
свежего остатка<=3дней и сверки opening; потенциальная калиброванная вероятность
дополнительно требует56дней. Это только data-gate, не подтверждение B6 калибровки.
До отдельного READY новой модели фабрика1.0 и опубликованные B4 числа не меняются.

Схема новых экспериментов до запусков: evaluation/EXPERIMENT-B5-B6.md. Сентябрь
не объявляется нетронутым holdout, заранее ограничены кандидаты и критерии принятия.

## model-registry-v2 и замороженная версия1.0

Контракт A-009 подтверждает get_forecast_service(model_version=None) и
get_supported_model_versions()->tuple[str,...]. Новый default с24.10 — seasonal-estimated-2.1-w84,
см. [политику модельной вероятности](estimated-probability.md). Версия2.0 остаётся закреплённой.
Она активирована отдельным F5 fallback-пакетом после зарегистрированного B6READY
и проверки совместимости приложения A. Это временное решение0082ec3, не ACK B.
Старые точные версии доступны для replay; сохранённые jobs/scenarios закрепляют1.0.
Поддерживаются baseline-repeat-week-0.1, seasonal1.0-w28/w56/w84,
seasonal-guarded-2.0-w84 и seasonal-estimated-2.1-w84.
Неизвестная версия (включая пустую строку/нестроковый вход) вызывает
UnsupportedModelVersionError(ValueError) с code unsupported_model_version.
A передаёт закреплённую run.model_version worker, несовпадение не считается новымпрогнозом.

Реализация legacy_v1 замораживает математику и транзитивные зависимости категоризации,
регулярностей и сценариев от B4/331b6f2. MANIFEST.json и12golden-выходов на синтетических
fixture закрепляют их; новые правила продукта не влияют на старые IDs.
Старые jobs не получают улучшенную математику под прежним именем. Общий resource/input
boundary quality-v2.0 явно отвергает неподдерживаемый вход, не меняет валидные суммы.
Новые модели/параметры/gates будут иметь другие model_version; default только отдельнымREADY.
Для побитового воспроизведения исторических B4 source_fingerprints нужен checkout331b6f2;
новые отчёты сравнивают frozen legacy численно и хранят собственный манифест.
## B5: исследовательские альтернативы до смены default

`v2/engine.py` сравнивает фиксированные EWM weekday (half-life28), winsor weekday
(95-й перцентиль по weekday/направлению) и ограниченный trend (shrink0.25,0.75–1.25),
окно84,200 парных недельных траекторий. Названия `research-weekday-…-2.0-w84-p200`
не зарегистрированы как продуктовый default. Winsor меняет модельные наблюдения,
исходные операции остаются неизменными. Расчёт статистики начинается после последней
несверки, recurrence при несверке использует только пригодное окно. Ненаблюдаемые дни
условно нулевые с предупреждением. При короткой/устаревшей истории вероятности None.

Один seed и независимый RNG каждой траектории сохраняют общий префикс при смене
горизонта и парность базового/сценарного расчёта. `daily_components` объясняет ожидаемые
потоки; медиана траекторий может отличаться от накопленного среднего потока.
Raw probabilities помечены исследовательскими и не являются проверенной калибровкой.
Вход ограничен quality-v2.0 и бюджетом сопоставления5M; календарные/сценарные ошибки
возвращаются как ForecastInputError, а не исправляют факты.

Запуск фиксированной selection-фазы (из корня, Python окружения backend):
`backend/.venv/Scripts/python.exe evaluation/select_v2.py --zip ../cashflow_dataset_participants.zip --output evaluation/selection-v2.json`.
Фазы, split и acceptance gate закреплены до запуска в evaluation/EXPERIMENT-B5-B6.md.
Отчёт содержит source hashes, общие folds, отсечения, cohorts, company macro, runtime
и профиль Python allocator на горизонтах1/7/30/90/180. Peak allocator не является RSS.

## B6: продуктовый quality/fallback и пределы доказанного риска

Версия `seasonal-guarded-2.0-w84` использует выбранную B5 математику frozen1.0-w84.
Вход проверяется quality-v2.0; после несверки вся статистическая/recurrence история
ограничена пригодным периодом. При непригодной симуляции p10/p90 схлопываются к p50.
На нормальной согласованной истории потоки/квантили1.0 сохраняются; None вероятности
является намеренным продуктовым поведением, отдельным от нулевого риска.

`risk-policy-2.0-withheld-new-gap`: probability_negative и probability_any_negative
всегдаNone, risk.available=False. Firstnegative/maxdeficit и минимум p50 остаются
доступны. Причина — недостаточно подтверждённых НОВЫХ разрывов; уже отрицательный
начальный остаток не доказывает заблаговременный прогноз. Details содержит quality,
risk_probability.status/reasons, версию политики и experiment ID. Для других горизонтов,
сценариев и явных будущих планов добавляется соответствующая причина отсутствия
подтверждённой калибровки. Нет переноса30-дневной калибровки молча.

Исследовательский B6 отдельно fit/check/test по EXPERIMENT-B5-B6.md сравнивает raw,
Beta(1,1)константу, logit-intercept и monotonePAVA. Daily/horizon раздельны; после обоих
преобразований horizon>=max(daily). Порог выбирается наcheck поF2 с FPR=FP/(FP+TN)<=25%.
Report содержит reliability/ECE/Brier,TP/FP/FN,Wilson95,company-bootstrap500 и leadtime
только для неотрицательногоopening. Нельзя подменять None нулём или называть сентябрь
новым нетронутым периодом. Дополнительный аудит openingnegative/persistence явно posthoc,
параметры не меняет; он вправе запретить продуктовую вероятность.

Команда из корня:
`backend/.venv/Scripts/python.exe evaluation/calibrate_v2.py --zip ../cashflow_dataset_participants.zip --output evaluation/calibration-v2.json`.
Фиксированный выбор метода берётся из selection-v2.json. Product fallback проверяется
отдельно от research risk scores на всех пригодных retrospectivefolds. Изменение quality
может менять pointfallback после несверки; такиеfolds и ошибка раскрыты отдельно.

Daily components различают planned/recurrence/scenario_expense/irregular и согласованы
с inflow/outflow. Объяснение risk_minimum указывает дату/сумму p50 и ссылки на outgoing
sources до минимума, а не только до первого минуса; это описание компонентов, не
гарантированная причинность. Сырые назначения не попадают в объяснения/логи.

Все зарегистрированные версии проверяют денежный диапазон результата<=9e15копеек
по модулю до записи в БД/JSON. Frozenseasonal дополнительно имеет guard стоимости
исторической сверки/memberlist/occurrence5M и<=500groups; превышение даёт явный
forecast_resource_limit, математика допустимых legacy входов не меняется. Новая версия
получает явный invalid_scenario/invalid_forecast_input при неподдерживаемой календарной
границе; старые1.0 не заменяются новым методом молча.
