# CashCast · Нейролептик

Сервис прогноза денег для малого бизнеса: загрузить банковскую выписку, увидеть
категории и ежедневный остаток, учесть будущий платёж, проверить сценарий «что если».
Одна компания/один счёт за расчёт, RUB. Интерфейс сейчас минимальный, использует
настоящие API, PostgreSQL и worker. Фронтенд будут перерабатывать отдельно.

## Что работает

- ИИ-ассистент DeepSeek V4.1 Flash 1017: чтение данных и рекомендации, настоящие
  графики/таблицы в чате, CSV preview. Создание планов, смена категории, импорт,
  сверка, прогноз и сценарий выполняются только отдельной кнопкой подтверждения.
  Инструкция и ограничения: [ассистент](specs/assistant.md).

- Cookie-сессия, CSRF и изоляция компаний; owner меняет данные, viewer только читает.
  Список доступных счетов; роль проверяется по целевой компании, включая ручки с UUID объекта.
  В кабинете viewer видит данные и историю без кнопок записи; переключение компании
  заново определяет её права. Ограничения также независимо проверяет сервер.
- CSV preview с ошибками строк, подтверждение импорта, защита от дублей, пагинация операций.
- Пресет организаторского датасета: UTF-8 BOM, `;`, «Поступление/Списание», ИНН как строка.
- Строгий разбор денег и направлений: ошибки CSV показываются до commit; повторные
  параллельные загрузки одного файла возвращают один импорт.
- Изменённое содержимое прежнего банковского ID отклоняет весь новый файл,
  включая новые операции и остатки; одинаковый факт и ручная категория сохраняются.
  Разные контрагенты с одним старым fingerprint без ID тоже дают конфликт, а не потерю факта.
- CSV счетов/обязательств через API: preview/атомарный commit, известная дата и
  происхождение, повтор без сброса оплаты, конфликт изменённого исходного документа.
- Автокатегории и ручная категория через API и кабинет; календарные регулярности.
- Неизменяемый вход задания, фоновые расчёты, p10/p50/p90, причины и происхождение результата.
- История сохранённых прогнозов и сценариев с пагинацией; открытие после перезагрузки
  страницы без нового расчёта и без изменения старого результата.
- Плановые события и план-факт: безопасные однозначные оплаты, частичный остаток,
  блокировки от двойного распределения; неоднозначность остаётся предложением,
  пока пользователь не проверит реквизиты и явно не подтвердит выбранную сумму.
- Четыре сценария API: перенос платежа, снижение нерегулярных поступлений,
  дополнительный расход, увеличение регулярного потока. Сравнение сценария с базой.
- В UI: вход → импорт → операции → 30-дневный прогноз/причины → четыре сценария
  → дневное сравнение; ручной план, CSVобязательств, источник и отмена плана.
  План-факт показывает связанные оплаты/остатки и явную безопасную автосверку.
  В предложениях можно проверить банковскую операцию и подтвердить полную или частичную оплату.
  В операциях можно изменить категорию; повторный импорт не стирает ручной выбор.
  «История расчётов» открывает прежний прогноз или сценарий; из сценария можно вернуться к базе.
  Композиция нескольких сценарных изменений доступна через API.
- После успешного импорта/изменения плана/сверки/категории кабинет сам запрашивает
  новый прогноз и ожидает worker. Старые результаты остаются в истории.
- Новые фактические операции, изменения планов и движение даты вперёд обновляют
  сохранённое состояние прогноза частично; UI/API показывают режим и счётчики.
  Первый запуск, другой горизонт/seed/модель и сценарии требуют full.
  [Как проверить](docs/check-incremental-forecast.md).

Новые расчёты используют **seasonal-guarded-2.0-w84**. Проверка не подтвердила
вероятность нового кассового разрыва, поэтому проценты возвращаются как недоступные,
а дата/дефицит по медиане и источники сохраняются. Старые расчёты1.0 остаются
неизменными. Ограничения и воспроизводимые числа: [evaluation/B6-REPORT.md](evaluation/B6-REPORT.md)
и [evaluation/REPORT.md](evaluation/REPORT.md). Эмпирический диапазон не является гарантией.
Расширенная аналитика B5–B10 ещё разрабатывается; её нельзя считать готовой по этому README.
Проверка по страницам исходного кейса и оставшиеся задачи:
[coordination/REQUIREMENTS.md](coordination/REQUIREMENTS.md).

## Запуск на одном устройстве

Нужны Git и Docker Compose v2; на Windows — Docker Desktop с Linux-контейнерами.
Python/Node на хосте для обычного запуска не нужны. Команды выполняются из корня клона.
Первая сборка скачивает образы/зависимости; далее используются кэши.

До утреннего одобрения main общая проверенная ночная сборка находится в
`integration/night`. Для нового клона:

```bash
git clone --branch integration/night https://github.com/kirit0zxc/cashcast.git
cd cashcast
```

Нужен доступ к приватному репозиторию. После человеческого слияния итогового PR
обычный запуск возможен из main; агенты ночью main не обновляют.

PowerShell:

```powershell
Copy-Item infra/.env.example infra/.env
# Открой infra/.env: при необходимости измени WEB_PORT и демо-пароль.
docker compose --env-file infra/.env -f infra/docker-compose.yml up -d --build
docker compose --env-file infra/.env -f infra/docker-compose.yml ps -a
curl.exe --fail http://127.0.0.1:8080/api/v1/health
```

Linux/macOS:

```bash
cp infra/.env.example infra/.env
docker compose --env-file infra/.env -f infra/docker-compose.yml up -d --build
curl --fail http://127.0.0.1:8080/api/v1/health
```

Открыть **http://localhost:8080**. При изменении WEB_PORT используй новый порт.
Демо-вход по умолчанию: **demo@example.com / demo-password**. Если менял значения —
используй CC_DEMO_EMAIL/CC_DEMO_PASSWORD. Seed создаёт пользователя только при его
отсутствии; смена env не меняет пароль существующего пользователя в volume.

`migrate` должен завершиться с кодом 0; `api`, `worker`, `web`, `postgres` работают.
Миграции применяются автоматически до старта API и worker. Сервис web слушает только
127.0.0.1; PostgreSQL и API не публикуются отдельно. Это локальное развёртывание.
Не открывай демо-пароли и HTTP-сессию в интернет: публичный TLS-деплой требует отдельной настройки.

Если расчёт окончательно завершился временным сетевым/DB-сбоем, устрани причину и
снова нажми «Рассчитать» с тем же вводом. Для известных временных ошибок/исчерпанной
lease сервер выдаст ещё3попытки тому же job/run без изменения сохранённого входа.
Пока задание выполняется, повторы не добавляют попыток. Ошибки данных, неизвестной
модели и неклассифицированные ошибки не возобновляются этим способом.

## Попробовать за несколько минут

1. Войди и выбери «Расчётный счёт».
2. Распакуй полученный отдельно ZIP и выбери **одну** `statements/C001.csv`.
   Нажми «Проверить файл», проверь ошибки, затем «Подтвердить импорт».
   Не загружай одновременно individual statements и `all_operations.csv`: это те же операции.
3. После импорта расчёт запустится автоматически на последний день выписки
   (в предоставленном C001 последняя операция — 2026-09-29). Дождись worker, посмотри
   график, причины и дневную таблицу. Для календарного среза 2026-09-30 выбери его явно.
   Для другого среза измени дату и нажми «Рассчитать».
4. Ниже выбери вид сценария. Для расхода укажи сумму/дату; для снижения выручки —
   процент; для задержки поступления или роста регулярного списания — платёж из
   сохранённого расчёта и дни/процент. Если подходящей цели нет, форма объяснит причину.
   «Проверить сценарий» покажет изменение по дням. База и фактические операции сохраняются.
5. Повторная загрузка того же файла возвращает прежний импорт и не создаёт новые операции.
   Подтверждение возвращает сохранённую сводку первого commit: «добавлено» в ней
   описывает результат того импорта, а не новые вставки при каждом нажатии.
6. В блоке «Будущие платежи и обязательства» добавь платёж с датой/суммой или раскрой
   загрузкуCSVобязательств. Ошибки исправляются до подтверждения. После сохранения
   дата среза переключится на сегодняUTC; кабинет сам запросит новый прогноз.
   В таблице видны остаток, статус, источник и отмена. Отмена сохраняет историю документа;
   повторный импорт того же CSV не восстанавливает отменённый платёж.
7. В «Сверке плана и факта» проверь связанные суммы и остатки. Просмотр только читает.
   «Применить однозначные совпадения» записывает безопасные связи с операциями;
   неоднозначные предложения остаются без оплаты. У предложения раскрой реквизиты
   банковской операции, проверь их и явно подтверди нужную полную или частичную сумму.
   После успешной сверки новая база запрашивается автоматически.
8. В таблице «Банковские операции» раскрой «Изменить категорию» у нужной строки,
   выбери значение и сохрани. «Выбрано вами» отличает ручную категорию от правила.
   Она сохраняется после повторного импорта; ранее сохранённый прогноз не меняется.
   Для учёта исправления кабинет сам запросит новый снимок на выбранную дату среза.
9. Под готовым прогнозом открой «Финансовый пульс»: дата возможной нехватки,
   варианты действий, стоимость финансирования и график эффекта относительно той же
   сохранённой медианы. Подушку можно задать в рублях, включая ноль; пустое поле —
   модельная оценка. Просмотр не меняет платежи и не запускает новый прогноз.
   Ниже — аудит расходов, зависимость от B2B-клиентов и стресс потери/задержки оплаты.
   «Источники и ограничения» показывает версии, ID расчёта и допущения.
   Пустые данные означают «Недостаточно данных», а не финансовое благополучие.

Пульс интегрирован из предоставленных модулей advisor/leaks; контракт и ограничения —
[specs/pulse.md](specs/pulse.md). Действия остаются гипотезами: сначала согласуй перенос
платежей, условия финансирования и достаточность данных. Остаток долга за пределами
горизонта показывается явно. Неподтверждённая вероятность разрыва не выводится числом.

Исторический прогноз не знает план, добавленный сегодня. Для проверки нового обязательства
создай его в кабинете или через API и пересчитай на текущую дату UTC. Устаревший остаток будет отмечен
предупреждением: это ограничение данных, а не новый банковский баланс.

Автоматическое обновление действует после успешных изменений в этом кабинете.
Открытие истории, reload, смена счёта или только редактирование даты не создают job.
При ошибке расчёта нет бесконечного автоматического retry. Изменения через другого
клиента/API требуют нового явного запроса: серверной подписки на внешние изменения нет.
При совместимом сохранённом состоянии новые фактические операции, исправления,
движение даты среза вперёд и изменения планов обновляют прогноз частично.
Worker переиспользует категории неизменённых операций, регулярности и состояние
траекторий. Первый запуск, смена горизонта/seed/модели и сценарии требуют полного
расчёта. Подготовка и валидация входного снимка в API по-прежнему читают историю.
Режим и счётчики видны в подробностях прогноза; [проверка](docs/check-incremental-forecast.md).

## API для фронтенда и интеграции

Префикс `/api/v1`; машинный контракт [specs/openapi.json](specs/openapi.json),
описание [specs/api.md](specs/api.md). JSON-схемы генерируются из Pydantic.
Все изменяющие запросы после login требуют cookie-сессии и `X-CSRF-Token` из `/auth/me`.
Суммы `*_minor` — целые копейки; `100000` означает 1000 ₽.
Viewer может читать списки/сохранённые результаты; изменяющие ручки, включая новый
прогноз/сценарий и CSVpreview, отвечают403read_only_company. При отсутствии членства404.
Управления приглашениями и ролями через кабинет пока нет; это не полный adminUI.

Основная цепочка:

```text
POST /auth/login → GET /auth/me
GET /companies/{company}/accounts → GET /import-presets
POST /companies/{company}/imports (multipart: file, account_id, mapping JSON)
POST /imports/{import}/commit
POST /companies/{company}/forecasts → job_id + forecast_run_id
GET /jobs/{job} до succeeded/failed
GET /forecasts/{forecast} и /forecasts/{forecast}/explanations
GET /forecasts/{forecast}/pulse?buffer_minor=0
POST /forecasts/{forecast}/scenarios → новое job
GET /forecasts/{scenario}/comparison
```

План: `POST /companies/{company}/planned-events`, например:

```json
{"account_id":"<UUID>","direction":"out","amount_minor":100000,
 "due_date":"2026-10-29","kind":"manual","counterparty_name":"Поставщик"}
```

План-факт: `GET /companies/{company}/plan-fact?account_id=<UUID>&as_of=YYYY-MM-DD`.
POST того же пути подтверждает только безопасные auto-сопоставления на сегодняшнем
UTC-срезе. Ручное подтверждение текущего предложения: POST
`/companies/{company}/plan-fact/confirm` с account_id, planned_event_id,
transaction_id и matched_amount_minor. Повтор той же пары/суммы безопасен; сервер
заново проверяет предложение и оба остатка, конфликт409 требует обновить список.
Закрытый paid/cancelled план нельзя возобновить или изменить его сумму409;
идентичный повтор сохраняет состояние. Исправление суммы активного плана до уже
оплаченной части закрывает остаток и переводит его в paid.
Исторический POST409; GET прошлого409, если план редактировался позже среза и его
прошлая версия отсутствует. `paid`/`cancelled` не возникают повторно из регулярностей.
Сверка ограничена100000парами «активный план × доступная операция»; превышение422,
без частичной оплаты/усечения кандидатов. Если после последнего банковского EOD
есть известные операции до среза, они входят в расчётный начальный остаток; это
явно подписано предупреждением и не выдаётся за новый подтверждённый банком EOD.

CSV обязательств: `POST /companies/{company}/obligation-imports` (multipart: file,
account_id, source_name, опциональный as_of), затем
`POST /obligation-imports/{import}/commit`. Шаблон
[evaluation/examples/obligations-demo.csv](evaluation/examples/obligations-demo.csv).
Используй реальные известные даты/суммы своего документа; пример синтетический.
Импорт с ошибками нельзя подтвердить частично. Минимальная форма этого импорта есть
в кабинете в блоке будущих платежей. Идентификатор внешнего документа
стабилен внутри счёта и source_name; повтор не отменяет оплату или ручную правку.
Новая сумма того же исходного ID — конфликт, а не молчаливое обновление.
Для банковской выписки сохраняй исходный operation_id. Без него разные источники с
одинаковым старым ключом и разным содержимым отклоняются409transaction_fingerprint_conflict;
полностью одинаковые платежи без ID неразличимы. Проверь счётчик повторов вpreview,
такие операции надёжно разделяются только исходными банковскими идентификаторами.
На счёт поддерживается до2000планов, включая закрытые; суммаостатков — до9e15копеек.
CSV сверх доступного лимита отклоняется целиком, а preview может разобрать до10000строк.

Проверка на отдельном локальном демо, создаёт синтетический счёт321руб:
`uv run python -m app.scripts.smoke_obligations --base-url http://127.0.0.1:8080 --write-demo-data`
(команда изbackend). Сравнивает реальный worker-прогноз до/послеCSV и проверяет повтор.

Примеры `changes` для сценария (один или несколько элементов в одном запросе):

```json
{"changes":[{"kind":"add_expense","amount_minor":100000,"on_date":"2026-10-29"}]}
{"changes":[{"kind":"delay_event","target_id":"<planned event UUID>","shift_days":7}]}
{"changes":[{"kind":"reduce_irregular_inflow","factor":0.8}]}
{"changes":[{"kind":"increase_recurring","factor":1.1}]}
```

Даты/цели должны существовать в зафиксированном входе и подходить виду сценария;
некорректный запрос422. Для increase нужна обнаруженная регулярность. Каждый сценарий
создаётся от исходной успешной базы; вложенный сценарий409. Сравнение требует того же
seed/входа/модели/горизонта, иначе409. Ошибки единые: `error.code/message/field_errors/request_id`.

## Данные и восстановление

PostgreSQL хранится в именованном volume `<compose-project>_pgdata`. Не меняй project name
при обычном перезапуске: это выберет другую БД. `stop`/`start`, `restart`, `down` без `-v`
сохраняют данные. **Не используй down -v для рабочего демо.**
Долгоживущие сервисы используют `restart: unless-stopped`: Docker перезапускает
завершившийся процесс, но уважает намеренный `stop`. Контейнер миграций одноразовый,
без автоперезапуска. Это не замена запущенному Docker Desktop и не кластерная HA.

```powershell
docker compose --env-file infra/.env -f infra/docker-compose.yml stop
docker compose --env-file infra/.env -f infra/docker-compose.yml start
docker compose --env-file infra/.env -f infra/docker-compose.yml logs --tail 60 api worker migrate
```

Резервная копия без преобразования бинарных байтов PowerShell-перенаправлением:

```powershell
docker compose --env-file infra/.env -f infra/docker-compose.yml exec -T postgres pg_dump -U cashcast -d cashcast -Fc -f /tmp/cashcast.dump
$taskPgId = docker compose --env-file infra/.env -f infra/docker-compose.yml ps -q postgres
docker cp "${taskPgId}:/tmp/cashcast.dump" ./cashcast.dump
```

Имена пользователя/БД заменить, если менял env. Дамп содержит финансовые данные:
храни отдельно от Git. Восстановление проверяй в отдельной пустой БД через `pg_restore`,
не поверх рабочего стенда. Резервная копия не заменяет исходный ZIP.

Проверка восстановления в **новом отдельном Compose project**, PowerShell
(defaults пользователя/БД cashcast; для другого env замени параметры):

```powershell
$taskRestoreProject = 'cashcast-restore-check'
$taskRestoreEnv = @{
  POSTGRES_USER='cashcast'; POSTGRES_PASSWORD='cashcast'; POSTGRES_DB='cashcast'
  CC_DATABASE_URL='postgresql+psycopg://cashcast:cashcast@postgres:5432/cashcast'
  CC_SEED_DEMO='false'; CC_APP_ENV='dev'; CC_COOKIE_SECURE='false'; WEB_PORT='18089'
}
$taskPreviousEnv = @{}
foreach ($taskKey in $taskRestoreEnv.Keys) {
  $taskPreviousEnv[$taskKey] = [Environment]::GetEnvironmentVariable($taskKey, 'Process')
}
try {
  # Process-env приоритетнее .env; API/worker/migrate явно используют новую local postgres.
  foreach ($taskKey in $taskRestoreEnv.Keys) {
    [Environment]::SetEnvironmentVariable($taskKey, $taskRestoreEnv[$taskKey], 'Process')
  }
  docker compose -p $taskRestoreProject -f infra/docker-compose.yml up -d --wait --wait-timeout 60 postgres
  if ($LASTEXITCODE -ne 0) { throw 'Тестовая PostgreSQL не готова' }
  $taskRestorePgId = docker compose -p $taskRestoreProject -f infra/docker-compose.yml ps -q postgres
  $taskTableCount = docker exec $taskRestorePgId psql -U cashcast -d cashcast -Atc "SELECT count(*) FROM pg_tables WHERE schemaname='public'"
  if ($LASTEXITCODE -ne 0 -or $taskTableCount -ne '0') { throw 'БД не пустая; восстановление остановлено' }
  docker cp ./cashcast.dump "${taskRestorePgId}:/tmp/cashcast.dump"
  if ($LASTEXITCODE -ne 0) { throw 'Копирование дампа не выполнено' }
  docker exec $taskRestorePgId pg_restore --exit-on-error --no-owner -U cashcast -d cashcast /tmp/cashcast.dump
  if ($LASTEXITCODE -ne 0) { throw 'Восстановление не выполнено' }
  docker compose -p $taskRestoreProject -f infra/docker-compose.yml up -d --build
  # Открой http://localhost:18089, войди учётной записью из восстановленного дампа.
} finally {
  foreach ($taskKey in $taskRestoreEnv.Keys) {
    [Environment]::SetEnvironmentVariable($taskKey, $taskPreviousEnv[$taskKey], 'Process')
  }
}
```

Повторный запуск инструкции на уже заполненной БД останавливается до pg_restore.
Исходный Compose project и volume не изменяются. `finally` возвращает прежние
переменные окружения, в том числе WEB_PORT. Ночная проверка восстановления и очереди:
[coordination/A22-RESILIENCE.md](coordination/A22-RESILIENCE.md).

## Проверки разработки

Для редизайна можно запускать frontend отдельно поверх работающего Compose.
Нужен Node24; из корня проекта в PowerShell:

```powershell
cd frontend

# Для обычного Compose на8080 эту переменную задавать не нужно.
# Текущий стенд владельца использует18086:
$env:CC_DEV_API_TARGET='http://127.0.0.1:18086'

```

Открыть **http://127.0.0.1:5174**. По умолчанию `/api` проксируется на
`http://127.0.0.1:8080`; адрес меняется через `CC_DEV_API_TARGET` до запуска Vite.
На Linux/macOS: `CC_DEV_API_TARGET=http://127.0.0.1:18086 npm run dev` из frontend.
Cookie-сессия и CSRF работают на origin dev-сайта. При занятом5174 Vite завершится
с ошибкой: проверь процесс/адрес, автоматического перехода на другой порт нет.
Dev-сервер привязан к127.0.0.1. Порты5173/8000 другого проекта не используются.

Python3.12 + uv0.13.5, Node24.18.1; зависимости закреплены backend/uv.lock и frontend/package-lock.json.
Из backend: `uv sync --frozen`. Чистая аналитика: `uv run pytest tests/analytics -q`.
Полный backend требует отдельную PostgreSQL БД с суффиксом `_test`: fixtures очищают её.
Никогда не указывай БД демо для тестов.

Если test-контейнер уже есть, используй `docker start cashcast-test-db`. Frontend:
`npm ci`, `npm run lint`, `npm run typecheck`, `npm run test:unit`, `npm run build` из frontend.
Unit-тесты используют встроенный Node24 test runner и чтение чистого TypeScript;
для них нужен Node24, как в CI/Docker, без дополнительных библиотек.
Для Chromium E2E подними отдельный Compose project на18081 с чистой БД, затем:
`npx playwright install chromium` и `npm run test:e2e`. Тест пишет синтетический CSV
в выделенное демо; это проверка интеграции, не качества модели.

В CI три обязательные проверки: backend/PostgreSQL/миграции/OpenAPI, frontend, чистый
Docker startup + Chromium E2E. Последняя также проверяет один workflow через Vite
с настоящим API/worker: StrictMode не должен дублировать автоматический POST или
оставлять кнопку расчёта заблокированной. Зелёный статус относится к точному проверенному SHA.

приватным, общий кандидат принимается по локальным тестам и независимому ревью;

Для E2E на отдельном порту можно задать CC_E2E_BASE_URL (по умолчанию18081).

## Оценка и ограничения

ZIP передаётся отдельно; [формат/контрольная сумма](specs/dataset-participants.md).
Не коммитить data/raw, CSV, .env, дампы и токены. Оценка из корня после uv sync:

```powershell
backend/.venv/Scripts/python.exe evaluation/backtest.py --zip data/raw/cashflow_dataset_participants.zip --phase validation --config evaluation/selected-config.json --output evaluation/validation.json
backend/.venv/Scripts/python.exe evaluation/backtest.py --zip data/raw/cashflow_dataset_participants.zip --phase holdout --config evaluation/selected-config.json --output evaluation/holdout.json
```

Опубликованный B4: validation517folds; отдельная сентябрьская оценка122folds, MAE
остатка1 072 364,48₽ против baseline2 775 628,60₽. Это ошибка в рублях, не «процент точности».
Вероятность горизонта хуже константы; короткая история не показала улучшения. Сентябрь
уже просмотрен, исправленный повтор не новый независимый holdout. Нет эталонных меток
категорий/счетов/налогового режима; confidence правил не является accuracy.

Дополнительный заранее заданный выбор point-метода: [B5-REPORT.md](evaluation/B5-REPORT.md),
268общихfolds на январе–марте. Новые методы не прошли критерий улучшения5%, поэтому
seasonal1.0-w84 сохранён. Сравнение/ресурсный профиль воспроизводимы, калибровку риска
этот эксперимент не доказывает. Команда: `python evaluation/select_v2.py --zip <ZIP> --output <report.json>`.

Нет живого банка/1С, OCR, автоматического расчёта налогов и консолидации счетов.
Налоговые обязательства вводятся только по известным сумме/дате. До полноценной
истории планов действуют описанные ограничения исторического plan-fact. Риск на конец
дня, внутридневные кассовые разрывы по этим данным не определяются.

## Подключить ИИ-ассистента

В локальном `infra/.env` задайте `CC_OPENROUTER_API_KEY` (не коммитьте файл).
Модель по умолчанию — `deepseek/deepseek-v4.1-flash-1017`; не ставьте ключ в `VITE_*`.
Запустите из корня проекта:

```powershell
docker compose --env-file infra/.env -f infra/docker-compose.yml up -d --build
```

Compose применит миграции; секрет получает только API. Войдите в кабинет, выберите
счёт, откройте «Ассистент CashCast». Попробуйте «Покажи последний прогноз и объясни
риски», затем «Предложи расход 5000 рублей на 30 октября 2026». До нажатия отдельной
кнопки подтверждения платёж не появляется. Отмена не меняет финансы.

График показывает сохранённый расчёт; новый прогноз или сценарий требует кнопки.
CSV прикрепляется в раскрывающемся разделе чата: preview → проверить сводку →
подтвердить. Ошибки файла исправляются до импорта. Загрузка/подтверждение CSV сами
не отправляют файл модели. Для полноценного совета сначала импортируйте историю и
рассчитайте прогноз. Без ключа отключён только текстовый ассистент, кабинет работает.

Дневной лимит: `CC_ASSISTANT_DAILY_TURNS=100` на пользователя (UTC). Расходы ключа
дополнительно ограничьте в OpenRouter. Модель получает сообщения и обезличенные
показатели выбранного счёта; не вставляйте в чат секреты. «Очистить чат» убирает
видимую историю, но не удаляет серверный журнал предложений и ответов.
