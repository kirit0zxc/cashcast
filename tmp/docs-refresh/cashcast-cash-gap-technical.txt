1. Что изменилось в PR #60
Формулы сезонного прогноза, bootstrap и суммы дефицита не менялись. Исправлены
интерпретация исторического среза, отображение медианного минуса и статусы финансового
пульса при недостаточной истории.
• Даты и суммы по медиане не зависят от risk.available.
• Уже отрицательный начальный остаток учитывается на дату as_of.
• Положительная медиана подписывается «не выявлен по медиане»; отсутствие будущих точек
обозначается отдельно. null вероятности не превращается в 0%.
• Пульс не показывает ok при недостаточном качестве, если нет watch/risk.
• Список планов на сегодня не выдаётся за календарь исторического frozen-прогноза.
2. Архитектура и поток данных
В браузере используется React/TypeScript. Серверная часть - FastAPI; PostgreSQL хранит
входные снимки, задания, результаты и дневные точки. Worker выполняет закреплённую версию
прогноза. Текущий default - seasonal-estimated-2.1-w84.
Вход прогноза -> worker -> сохранённые p50 и детали -> CashGapReader -> CashGapService ->
CashGapOut -> CashGapPanel.
CashGapReader проверяет доступ к компании, статус succeeded, полноту и согласованность
сохранённого входа с run. Загружает точки в порядке дат и вызывает вычислительный сервис.
Несуществующий/чужой прогноз даёт 404, неготовый или неполный сохранённый источник - 409.
Проверки денежных/ресурсных границ сохранены.
CashGapService выделяет эпизоды и рассчитывает гипотезы. FrozenPulseService.curve
восстанавливает разложение сохранённой медианы на календарные, статистические потоки и
поправку к медиане. Интерфейс показывает сводку, причины и сравнение кривых.
Старые run не переводятся на новую модель; для нового процента нужен новый расчёт. Отчёт
всегда относится к конкретным forecast_id, model_version и data_version.
3. Исторический срез и качество
Операции и остатки ограничены датой <= as_of. У планов дополнительно проверяется available_at
<= as_of; будущая дата платежа сама по себе не доказывает, что план был известен в прошлом.
В календарь входят потоки в пределах горизонта.

восстановления существующего. Длительность открытого/существующего эпизода может быть

delay задаёт flow_id и более позднюю дату внутри горизонта; один поток переносится один раз.
Расход допускается переносить только для разрешённой закупки с явным payment_delay_agreed.
Налоги, зарплата, аренда, кредит и неизвестный расход защищены. Задержка поступления -
стресс ухудшения.

процентную ставку. Получение после среза внутри горизонта; возврат позже получения.

быть отрицательным. API принимает до трёх действий, текущая форма интерфейса отправляет
одно действие.
6. Пульс и доступность вероятности
risk.available описывает вероятность. Качество пульса определяется отдельно: cash_reliable =
details.quality.eligible_for_simulation. Если у старого результата нет этого поля, качество
рассчитывается по его сохранённому входу, не по live-данным.

пульс быть unknown.
7. Регрессии и честные метрики
Пример PR #60 синтетический: срез 01.08.2026, данные начинаются 27.07, доступны 6
календарных дней. Начальный остаток 260 400 ₽, минимум p50 247 900 ₽, конец 30-дневного
горизонта 289 500 ₽. Медианного разрыва нет; вероятность null; cash unknown, общий пульс не ok.
Перенос среза назад сам не создаёт минус.
Известный на срезе расход 400 000 ₽ на 03.08 создаёт разрыв с этой даты с максимальной
нехваткой 152 100 ₽ даже при недоступной вероятности. Такой же план, доступный только с 24.10,
не влияет на августовский расчёт. Проверки также покрывают длинную историю, раздельные
пороги 28/56 дней и legacy-результат без quality.
UI unit-тесты покрывают положительный ряд без процента, отрицательный ряд без процента,
отрицательный opening с последующим восстановлением и отсутствие точек. Изолированный
browser-тест использует подставные ответы API; он не доказывает сквозную работу БД/worker и
не измеряет точность прогноза.
Исследовательский CatBoost на Berka не включён в продукт. На отдельных счетах v1 дал TP=6,
FP=14, FN=5: precision 30%, recall 54,55%. V2: TP=6, FP=15, FN=5; предупреждения не
улучшились. release.allowed=false. Эти числа не являются точностью seasonal 2.1. Отображение
некалиброванного процента не меняет метрики.
