# 10 — календарная структура потоков и отделение от уровня баланса

approved по активной цели; до реализации. Источник: мой выбор следующей гипотезы
после09. Условный CDF снизил FP, но не сохранил поздний recall. Вместо подбора
порога по позднему промаху изменяем признаки по экономическому смыслу и проверяем абляцию.

Два семейства с CatBoost depth4/6 и прежними монотонными query-ограничениями:
1. flow_only: прежние признаки09 без начального остатка, минимума исторического
   остатка и доли отрицательных остатков. Порог query остаётся отдельным входом.
2. calendar: те же flow_only плюс прошлые потоки до365дней после последней несверки,
   дневные/месячные масштабы и профили дня месяца. Будущие календарные даты известны;
   суммы берутся только из прошлых наблюдений соответствующего дня месяца.

Профиль: среднее и медиана по входящим/исходящим потокам для каждого дня месяца;
сумма ожидаемых значений ближайших7/14/30дней, доля дней с операциями, квантиль .9
размера дня, средний/максимальный месячный netflow. Нули считаются днями без операций
только внутри сверенной истории; причинность и границы проверяются.

Прежнее обучение09, горизонты/сетка порогов/веса, 600итераций, без изменений целей.
Глобальный выбор из4моделей по среднему естественному LogLoss на7/14/30 за январь—март.
Порог и AND/OR с текущим риском — те же правила января—июня09. Затем все пять фаз08.
Сначала сохранить состав/порог, затем оценивать поздние фазы. Приватные строки только
локально, никакой передачи реальных данных в API. Данные многократно просмотрены,
независимый контроль не заявляется. Балансовый ансамбль75/25 не меняется.

Тесты: отсутствие будущего, инвариантность flow_only к согласованному сдвигу
уровня баланса при сохранении потоков, длины/конечность, неизменность query-монотонности,
абляция сопоставляется на одинаковых строках. Сохранять плохие результаты тоже.
Если удаление баланса ухудшает прогноз из-за пополнений владельца, считать это
результатом опыта, а не скрывать влияние. Гарантий выигрыша и публикации нет.
