# Локальный резерв: запуск и ограничения

Основа: CashCast `a92bd5013b5b5d7e5008157815160b67fd762edf`.
Пакет добавляет исследовательские файлы в отдельную копию этого коммита. Он не меняет
фабрику модели, HTTP API, зависимости backend, базу или развёрнутый сайт.

## Уже работает на этом компьютере

Из `work/cashcast-model-fallback`:

```powershell
$env:HF_HUB_OFFLINE='1'
$env:HF_HUB_DISABLE_PROGRESS_BARS='1'
$env:PYTHONIOENCODING='utf-8'
& '../cashcast-chronos-env/Scripts/python.exe' -m evaluation.liquidity_risk.local_compare `
  --snapshot data/raw/local-comparison-demo/synthetic-snapshot.json `
  --model-info journal/chronos-source.json `
  --output data/raw/local-comparison-demo/comparison-repeat.json
```

Результат — JSON с двумя независимыми наборами точек. `current` — текущая модель
и её исходная оценка риска; `candidate` — p10/p50/p90 Chronos и диагностический флаг
пересечения нуля нижним квантилем. Вероятность горизонта у Chronos остаётся `null`.
Показатель текущей модели тоже не объявляется калиброванным.

Вход — стандартный `ForecastInputCodec.encode(snapshot)`, версия 1. В него можно
передать снимок, подготовленный существующим backend, сохранив его **локально**.
Программа не подключается к БД и не выгружает выписки в облако. Сам снимок может
содержать чувствительные строки, поэтому не коммитить и не передавать его как отчёт.
При планах, сценарии, явных регулярностях DTO, горизонте не 30 дней или плохой истории
кандидат получает `unavailable`; результат текущей модели сохраняется.

Пример в архиве синтетический и проверяет исполнение, а не качество предсказания.
Кандидат остаётся `research_only`, `release_allowed=false`.

## На другом компьютере

Создать отдельную копию указанного main и распаковать добавочные файлы из архива
в её корень. Установить **отдельное** Python 3.12 окружение; зависимости приложения
не менять. Версии исследовательских сред находятся в `journal/ENVIRONMENTS.json`.
Chronos-окружению нужны `chronos-forecasting==2.3.2`, `torch==2.14.1+cpu` (официальный
CPU index PyTorch), `transformers==5.20.2`, `numpy==2.5.4`, `pandas==3.1.0`.
CatBoost-экспериментам — отдельное окружение с `catboost==1.2.8`, NumPy и pandas тех же версий.

Весов Chronos в архиве нет. Официальный источник:
[amazon/chronos-2](https://huggingface.co/amazon/chronos-2), Apache-2.0,
revision `29ec3766d36d6f73f0696f85560a422f50e8498c`.
Скачать именно этот revision через `huggingface_hub.snapshot_download`, записать
возвращённый путь в поле `snapshot` файла `journal/chronos-source.json`.
Другие поля оставить как есть. После загрузки установить `HF_HUB_OFFLINE=1`.
Старый абсолютный путь в метаданных относится только к текущему компьютеру.

## Повторение экспериментов

У каждого `experiments/01_…py`–`07_…py` есть `--help`; протоколы рядом в `journal`.
Исходный организаторский ZIP не включён. Его SHA-256 зафиксирован в отчётах; загрузчик
экспериментов намеренно отклоняет другую версию вместо молчаливого смешивания выборок.
Для нового контрольного файла готовится обычный снимок приложения, а не подменяется SHA.
Для измерения качества нужны последующие фактические остатки; один прогноз метрик не даёт.

Результаты повторного запуска складывать в новый `--output`, исходные результаты
не перезаписывать. Для 06 нужны локальные промежуточные строки 02, для 03 они также
используются: эти приватные файлы не включены, их восстанавливает повтор 02.
Модели 01/02/04 обучаются на прошлом; 05/07 используют уже предобученный Chronos без дообучения.

## Проверки

```powershell
& '../cashcast-eval-env/Scripts/python.exe' -m unittest `
 evaluation.fallback_model.test_model evaluation.liquidity_risk.test_risk `
 evaluation.liquidity_risk.test_extensions evaluation.liquidity_risk.test_final -v
```

39 уникальных тестов: причинность, денежные единицы, редкие события, неизменность
пороговых решений, отсутствие ложной вероятностной семантики, неподдержанные входы,
повреждённые выходы модели. Ещё прошли 77 чистых аналитических тестов CashCast и
13 проверок весов/воспроизводимости 01. PostgreSQL для этих проверок не нужен.

## Решение о внедрении

Ни один новый вариант риска не прошёл все заранее заданные проверки.
Chronos полезен для сравнения кривой и исследовательского предупреждения, но его
медиана сама по себе пропустила все 4 новых поздних разрыва. Заменять детектор
проверкой `p50 < 0` нельзя. Коррекция вероятностей 06 тоже не выпускается: Brier
остаётся хуже постоянной оценки по частоте событий, а дневной/горизонтный риск
требует согласованных совместных траекторий.

Следующий решающий шаг — независимый контроль с заранее зафиксированными моделями,
одинаковыми окнами и раздельными метриками остатков и новых разрывов. Правильный
результат — честно измеренное качество, а не обещание максимальных метрик заранее.
