## Команда и границы

- **Диана** — frontend (`frontend/`).
- **Пользователь (тот, кто тебя запустил)** — backend + инфраструктура, интегратор, единственный владелец миграций. Ты работаешь за него.
- **Данил** — прогноз и риск (`backend/app/modules/forecasting/`, `evaluation/`).
- **Дима** — категоризация, регулярности, плановые события (`backend/app/modules/categorization/`, `planning/`).

Ты строишь **каркас и общие контракты**, по которым все четверо начнут работать параллельно. Чужую логику (модель прогноза, правила категорий, экраны UI) не реализуешь — только интерфейсы, заглушки с понятным `NotImplementedError`/TODO и типизированные фикстуры.

## Цель (часы 0–4 по плану)

К концу работы у команды есть:

1. **Репозиторий** со структурой из плана:
   ```
   frontend/src/features/{imports,transactions,forecast,planning,scenarios}
   backend/app/{core,api,modules/{imports,categorization,planning,forecasting,jobs}}
   evaluation/  specs/  infra/
   ```
   Рабочее название продукта — плейсхолдер, не HoneyForge и не копия его кода.
2. **`docker compose up`** поднимает web (Vite/nginx), api (FastAPI), worker (тот же образ, другая команда), postgres. Наружу публикуется только web; БД и worker закрыты. Версии закреплены, lock-файлы есть.
3. **Backend-скелет:** Python 3.12, FastAPI, Pydantic v2, SQLAlchemy 2, Alembic, pytest, Ruff. Конфиг через env (`infra/.env.example`), единый формат ошибки `{error:{code,message,field_errors,request_id}}`, `GET /api/v1/health`.
4. **Первая миграция** с сущностями из плана (раздел «Данные, которые нужны всем»): `company`, `account`, `user`, `import`, `transaction`, `daily_balance`, `planned_event`, `forecast_run`, `forecast_point`, `job`. Деньги — целые копейки (`amount_minor`, BIGINT) + `direction in/out`, никакого float. `daily_balance` отдельно от операций. Уникальные ключи для идемпотентного импорта и версии входа прогноза.
5. **Контракт v1** — `specs/api.md` + OpenAPI, сгенерированный FastAPI из Pydantic-схем, с ручками из плана (auth, imports+commit, transactions, planned-events, forecasts → 202 + job, jobs/{id}, forecasts/{id}, explanations, scenarios). Ручки, которые ещё не реализованы, отвечают `501` с корректной схемой ответа.
6. **JSON-фикстуры** в `specs/examples/`: успешный прогноз с разрывом, прогноз без разрыва, недостаток истории, некорректный CSV. Из них Диана поднимает MSW, Данил и Дима — тесты.
7. **Python-интерфейсы модулей** (чистые сервисы без HTTP), чтобы Данил и Дима сразу писали внутрь:
   - `ForecastService.run(input: ForecastInput) -> ForecastResult` (as_of, horizon, data_version, model_version, seed; точки p10/p50/p90, `probability_negative` по дню и отдельно на горизонте).
   - `Categorizer.categorize(txns) -> list[CategoryAssignment]` (категория + причина + confidence; неизвестное = `other`, не угадывать).
   - `RecurrenceDetector.detect(txns, as_of) -> list[RecurrenceGroup]`.
   - `PlannedEventMatcher` — сопоставление план/факт без двойного счёта.
8. **Worker:** очередь заданий в PostgreSQL (`SELECT … FOR UPDATE SKIP LOCKED`, lease + повтор), статусы pending/running/succeeded/failed. Пока выполняет заглушку прогноза — тупой baseline «повтор последней недели», чтобы путь CSV → БД → прогноз → JSON работал сквозь.
9. **CI** (GitHub Actions): Ruff + pytest с Postgres-сервисом + миграции up; frontend lint + typecheck + build. Красный тест не отключать.
10. **Демопользователь и компания** через сид-скрипт; логин через HttpOnly cookie. Тест: пользователь A не видит компанию B.
11. **`README.md`**: как поднять за одну команду, где что лежит, кто владелец какой папки, правила (main только через PR, русские комментарии, спеки актуальны, деньги не float).
12. **`specs/questions-for-mentor.md`** — вопросы из раздела «Старт» плана плюс то, что ты сам заметил.

## Правила

- Комментарии в коде — по-русски, объясняют допущения и причины, а не пересказывают код.
- Модульный монолит, никаких микросервисов, WebSocket, GPU, LLM в основной цепочке.
- Никаких выдуманных метрик и «точности 95%» нигде — ни в README, ни в фикстурах (числа в фикстурах помечены как синтетические).
- Назначения платежей, реквизиты, токены и содержимое файлов не пишутся в логи.
- Датасета ещё нет: формат CSV-парсера делай настраиваемым (маппинг колонок), реальные имена полей уточним после получения данных. Не подгоняй схему под догадку.
- Маленькие осмысленные коммиты. Не пушь и не создавай удалённый репозиторий без моего подтверждения.
- Если упираешься в решение, которое меняет общий контракт или распределение ролей, — остановись и спроси.

## Готово, когда

- `docker compose up` с чистой БД поднимает всё, `/api/v1/health` = ok, фронт открывается.
- `pytest` зелёный, включая интеграционный тест: логин → загрузка тестового CSV → commit → запрос прогноза → job succeeded → GET прогноза отдаёт 30 точек.
- Повторная загрузка того же файла не создаёт дубли.
- OpenAPI и `specs/examples/` согласованы (тест валидирует фикстуры против схем).
