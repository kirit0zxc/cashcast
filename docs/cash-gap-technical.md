# CashCast: техническая реализация кассовых разрывов

Версия документа: 24.10.2026. Источник: `origin/main`, commit
`60147f01e4627c0f065170cc02ab451219b3020f`, tree
`a62d52df1b93a3c86e8bcca0f476f6d179c378b5`.

Документ описывает PR #53, #55, #56, #59 и последнее исправление PR #60.
Исследовательские метрики отделены от поведения продуктовой модели.
Математические формулы приведены в [отдельном документе](cash-gap-mathematics.md).

## 1. Что изменилось в PR #60

Формулы сезонного прогноза, bootstrap и суммы дефицита не менялись.
Исправлены интерпретация исторического среза, отображение медианного минуса и
статусы финансового пульса при недостаточной истории.

- Даты и суммы по медиане не зависят от `risk.available`.
- Уже отрицательный начальный остаток учитывается на дату `as_of`.
- Положительная медиана подписывается «не выявлен по медиане»; отсутствие будущих
  точек обозначается отдельно. `null` вероятности не превращается в 0%.
- Пульс не показывает `ok` при недостаточном качестве, если нет `watch/risk`.
- Список планов на сегодня не выдаётся за календарь исторического frozen-прогноза.

## 2. Архитектура и поток данных

В браузере используется React/TypeScript. Серверная часть - FastAPI; PostgreSQL
хранит входные снимки, задания, результаты и дневные точки. Worker выполняет
закреплённую версию прогноза. Текущий default - `seasonal-estimated-2.1-w84`.

Вход прогноза -> worker -> сохранённые p50 и детали -> CashGapReader ->
CashGapService -> CashGapOut -> CashGapPanel.

`CashGapReader` проверяет доступ к компании, статус `succeeded`, полноту и
согласованность сохранённого входа с run. Загружает точки в порядке дат и вызывает
вычислительный сервис. Несуществующий/чужой прогноз даёт 404, неготовый или
неполный сохранённый источник - 409. Проверки денежных/ресурсных границ сохранены.

`CashGapService` выделяет эпизоды и рассчитывает гипотезы. `FrozenPulseService.curve`
восстанавливает разложение сохранённой медианы на календарные, статистические
потоки и поправку к медиане. Интерфейс показывает сводку, причины и сравнение кривых.

Старые run не переводятся на новую модель; для нового процента нужен новый расчёт.
Отчёт всегда относится к конкретным forecast_id, model_version и data_version.

## 3. Исторический срез и качество

Операции и остатки ограничены датой `<= as_of`. У планов дополнительно проверяется
`available_at <= as_of`; будущая дата платежа сама по себе не доказывает, что план
был известен в прошлом. В календарь входят потоки в пределах горизонта.

История ограничивается 84 календарными днями и начинается после последней несверки.
Количество пригодных дней - длина календарного окна, не число операций. Пропуски
условно нулевые; это явное допущение полноты выгрузки.

| Условие | Что доступно |
|---|---|
| Менее 28 пригодных дней или нет свежего согласованного остатка | Точечный/плановый fallback, p10=p50=p90, вероятность null |
| 28-55 дней и свежий согласованный остаток | Симуляции и квантили; вероятность 2.1 ещё null |
| От 56 дней и свежий согласованный остаток, базовая симуляция успешна | Модельная вероятность 2.1 со статусом estimated_uncalibrated |
| Сохранённая версия 2.0 | Прежняя политика null сохраняется |

Свежий остаток: последний подтверждённый баланс не старше трёх дней, а его сумма
с последующими известными фактами равна opening. Нельзя трактовать недоступность
вероятности как отсутствие медианного дефицита.

## 4. Результат карточки

Дневной ряд включает opening на `as_of` и все сохранённые p50. Ноль закрывает эпизод.
Существующий минус (`existing`) начинается на срезе; новый (`new`) - позже, в том
числе после восстановления существующего. Длительность открытого/существующего
эпизода может быть только нижней границей.

| Группа полей | Содержание |
|---|---|
| base / preview | Статус, opening_already_negative, первый новый разрыв, дни до него, максимальная нехватка, резерв и суммарные отрицательные дни |
| episodes | Тип, начало, последний отрицательный день, восстановление, длительность, максимум дефицита и худшая дата |
| points | Дата, остаток базы, остаток гипотезы и разница |
| causes | Знаковое разложение исходного минимума с observed/planned/estimated/scenario |
| flows | Потоки, frozen source_ref и допустимость переноса |
| probability | Оценка для базы, статус и причина доступности; preview возвращает null |
| costs / warnings | Стоимость финансирования, долг за горизонтом, улучшение и ограничения |

`required_reserve_minor` равен максимуму дефицита: это постоянная добавка с начала
ряда без возврата. Финансирование с возвратом рассчитывается отдельно. Все `_minor`
передаются в целых копейках. Сумма `causes` точно равна `causes_balance_minor`,
но не доказывает причинность. Планы не являются фактическими оплатами.

Без отрицательных точек карточка возвращает `no_gap` только при пригодности
симуляции; иначе `insufficient_data`. При отрицательных точках возвращает `gap`
и сохраняет предупреждения о качестве.

UI helper `medianGap` в обзоре/прогнозе независимо читает opening+p50. Его первый
отрицательный день может быть датой существующего минуса и отличаться от
`first_new_gap_date` карточки. `hasForecast` означает наличие будущих точек;
opening без точек не подтверждает прогноз. Полностью пустой ряд даёт сумму null.

## 5. Гипотезы действий и API

| Метод и путь с префиксом /api/v1 | Поведение |
|---|---|
| GET /forecasts/{id}/cash-gaps | Читает карточку успешного frozen-прогноза |
| POST /forecasts/{id}/cash-gap-preview | Принимает 1-3 действия; без job и записи платежей |
| POST /forecasts/{id}/scenarios | Полный отдельный сценарный run; позволяет пересчитать вероятность |
| GET /models/quality | Общий обезличенный offline-отчёт исследований после входа |

Owner и viewer своей компании могут читать карточку и вычислять preview. POST
защищён CSRF. Доступность кнопок не заменяет серверную проверку компании.

`delay` задаёт flow_id и более позднюю дату внутри горизонта; один поток переносится
один раз. Расход допускается переносить только для разрешённой закупки с явным
`payment_delay_agreed`. Налоги, зарплата, аренда, кредит и неизвестный расход защищены.
Задержка поступления - стресс ухудшения.

`financing` задаёт дату получения, положительную сумму, дату возврата и полную
стоимость, не процентную ставку. Получение после среза внутри горизонта; возврат
позже получения. Списываются тело и стоимость. Долг за горизонтом виден отдельно.
`improvement_minor` может быть отрицательным. API принимает до трёх действий,
текущая форма интерфейса отправляет одно действие.

## 6. Пульс и доступность вероятности

`risk.available` описывает вероятность. Качество пульса определяется отдельно:
`cash_reliable = details.quality.eligible_for_simulation`. Если у старого результата
нет этого поля, качество рассчитывается по его сохранённому входу, не по live-данным.

Порядок выбора cash-статуса:

1. Нет денежных данных или потоков - unknown.
2. Минус в ближайшем проверяемом периоде - risk.
3. Остаток ниже подушки, опасный клиентский стресс или более дальний минус - watch.
4. Нет сигналов, но качество недостаточно - unknown.
5. Иначе - ok по сохранённой медиане.

Если cash unknown, спокойные другие блоки не превращают общий пульс в ok.
Сигналы watch/risk сохраняют приоритет. При 28-55 пригодных днях отсутствие процента
само по себе не вынуждает пульс быть unknown.

## 7. Регрессии и честные метрики

Пример PR #60 синтетический: срез 01.08.2026, данные начинаются 27.07, доступны
6 календарных дней. Начальный остаток 260 400 ₽, минимум p50 247 900 ₽, конец
30-дневного горизонта 289 500 ₽. Медианного разрыва нет; вероятность null;
cash unknown, общий пульс не ok. Перенос среза назад сам не создаёт минус.

Известный на срезе расход 400 000 ₽ на 03.08 создаёт разрыв с этой даты с максимальной
нехваткой 152 100 ₽ даже при недоступной вероятности. Такой же план, доступный только с 24.10, не влияет на
августовский расчёт. Проверки также покрывают длинную историю, раздельные пороги
28/56 дней и legacy-результат без quality.

UI unit-тесты покрывают положительный ряд без процента, отрицательный ряд без
процента, отрицательный opening с последующим восстановлением и отсутствие точек.
Изолированный browser-тест использует подставные ответы API; он не доказывает
сквозную работу БД/worker и не измеряет точность прогноза.

Исследовательский CatBoost на Berka не включён в продукт. На отдельных счетах v1
дал TP=6, FP=14, FN=5: precision 30%, recall 54,55%. V2: TP=6, FP=15, FN=5;
предупреждения не улучшились. `release.allowed=false`. Эти числа не являются
точностью seasonal 2.1. Отображение некалиброванного процента не меняет метрики.
