# Как проверить частичное обновление прогноза

Эта инструкция относится к версии с `calculation` в ответе прогноза.
Старые стенды без этой функции не показывают режим расчёта.

## В кабинете: 5 минут

1. Войдите на тестовый стенд. Для локального Docker demo:
   `demo@example.com` / `demo-password`. Выберите тестовую компанию и счёт.
2. В разделе «2. Прогноз на 30 дней» поставьте **сегодняшнюю дату UTC**
   и нажмите «Рассчитать». Дождитесь графика. Под ним/над ним будет режим.
   Первый новый запуск на этой версии — «Полный расчёт»; при повторе можно
   получить уже сохранённый результат. В раскрывающемся блоке «Дневные значения
   и происхождение расчёта» запишите ID прогноза и остаток на выбранную будущую дату.
3. В «Будущие платежи и обязательства» выберите «Расход», сумму **10 000 ₽**,
   дату **через 5 дней**, контрагента **Тест частичного обновления** (новое имя,
   не совпадающее с регулярными платежами). Нажмите «Добавить платёж».
4. Дождитесь автоматического обновления графика. Ожидается надпись
   **«Частичное обновление: календарь пересчитан, история и траектории переиспользованы.»**
   ID прогноза новый; источник истории указывает на предыдущий совместимый запуск;
   новых траекторий — **0**. До даты платежа значения прежние, с даты платежа
   медианный остаток ниже на **10 000 ₽**. Если он стал отрицательным, появится предупреждение.
5. В строке добавленного тестового платежа нажмите «Отменить». После нового
   обновления сумма вернётся; расчёт снова частичный. Через историю откройте
   первоначальный прогноз — он должен остаться прежним.

**Не начинайте с исторической даты выписки:** новый план известен только сегодня.
После его добавления UI переключит срез на сегодня, а смена среза требует full.
Сначала рассчитайте базу именно на сегодня. Старые модели/старые сохранённые run
без checkpoint не становятся частичными задним числом.

## Независимая проверка через Network

Откройте F12 → Network → Fetch/XHR. После добавления плана найдите
`GET /api/v1/forecasts/<новый-id>`. В JSON должны одновременно быть:

```json
{
  "status": "succeeded",
  "calculation": {
    "mode": "incremental",
    "reason": "planned_events_changed",
    "reused_history": true,
    "bootstrap_paths_generated": 0,
    "source_forecast_id": "id-совместимого-предыдущего-расчёта"
  }
}
```

Поля points содержат копейки: разница для 10 000 ₽ равна **1 000 000**.
Повтор кнопки «Рассчитать» без изменений может вернуть тот же ID — это
идемпотентность, а не новый частичный расчёт. Скорость ответа не является доказательством.

## Контроль полного пересчёта

Измените дату среза на ещё не рассчитанную или загрузите новую операцию в тестовый
счёт и рассчитайте прогноз с учётом этой даты. Должно быть `mode=full`,
`reason=no_compatible_checkpoint`, `source_forecast_id=null`. Это ожидаемый fallback:
новая фактическая история пока не обновляется инкрементально.
Для проверки перезапуска перезапустите только worker своего compose-проекта,
добавьте ещё один новый план на том же срезе: должно сохраниться incremental.

## Автотесты разработчика

Из backend на отдельной тестовой PostgreSQL (имя БД обязательно заканчивается `_test`):

```powershell
$env:CC_TEST_DATABASE_URL = 'postgresql+psycopg://USER:PASSWORD@localhost:PORT/cashcast_test'
$env:CC_DATABASE_URL = $env:CC_TEST_DATABASE_URL
.venv/Scripts/python.exe -m pytest tests/analytics/test_incremental_forecast.py tests/test_incremental_forecast.py
```

Тесты сравнивают partial с full и блокируют RNG/детектор на частичном пути.
Не направляйте их на БД кабинета: fixture очищает таблицы.

Из frontend, против отдельного тестового Docker-стенда без моков:

```powershell
$env:CC_E2E_BASE_URL = 'http://127.0.0.1:18093'
npm.cmd run test:e2e -- incremental.spec.ts
```

E2E добавляет синтетическую выписку и планы: используйте тестовую БД/счёт.
