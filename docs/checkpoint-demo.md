# Контрольный датасет: подготовка и показ

## Распределение

Данил отвечает за загрузку и валидацию файла. Эта поставка отвечает за временную
проверку действующей модели, метрики, журнал, графики и автономный отчёт.
Парсер и формат импорта здесь не заменяются.

Данилу после commit нужны `company_id` и `account_id`. Сохраняются операции
`BankTransaction` и достоверные остатки на конец дня `DailyBalance`:

- направление `in`/`out`, сумма — положительные целые копейки;
- остаток — целые копейки со знаком, именно EOD, а не промежуточный остаток;
- один счёт/валюта RUB; чужую валюту нельзя объявлять рублями;
- пропущенный остаток остаётся неизвестным; отсутствующие строки не создают нулей;
- повтор импорта не удваивает операции; разные компании не смешиваются;
- желательно SHA-256 исходного файла и установленная граница покрытия.

Полнота выписки — отдельное подтверждение. Не включать автоматически только потому,
что CSV прочитан без ошибок. Для иных столбцов используются существующие настройки
маппинга импорта. Неподдерживаемую схему нужно явно показать пользователю.

## Локальный запуск

Из корня репозитория, с работающим Docker Desktop в режиме Linux containers:

```powershell
$env:WEB_PORT = '18081'
docker compose -p cashcast-demo -f infra/docker-compose.yml up -d --build
docker compose -p cashcast-demo -f infra/docker-compose.yml ps
```

Открыть `http://localhost:18081`, войти `demo@example.com` / `demo-password`.
Это локальная демонстрационная учётная запись; публичный стенд отдельно защищается.
Должны работать web, api, worker и postgres. Для сохранения БД не выполнять `down -v`.
Логи worker: `docker compose -p cashcast-demo -f infra/docker-compose.yml logs --tail 50 worker`.

## Показ за 15 минут

1. **0–3 минуты.** Выбрать компанию/счёт, загрузить файл через «Импорт данных»,
   проверить preview и ошибки, подтвердить импорт. Сверить период, направления и EOD.
2. **3–5 минут.** Открыть «Проверка качества». Выбрать дату среза, на которой есть
   наблюдаемый EOD. Желательно оставить до неё не менее 84 дней, а после — фактические
   данные для выбранного горизонта. Например, для 3 окон по 7 дней нужен 21 день
   последующей истории и EOD на каждом срезе. Нельзя оценивать ещё не наступившее будущее.
3. Подтвердить полноту операций только при наличии основания. Порог 0.5 фиксируется
   до просмотра результатов; подгонять его по контрольным ответам нельзя.
4. **5–10 минут.** Нажать «Проверить качество». После завершения показать ошибки
   остатков/поступлений/списаний, три отдельные матрицы, графики, дневные расчёты
   и «Пошаговый журнал вычислений». Снять графики средствами браузера/ОС.
5. **10–12 минут.** Скачать HTML с графиками и полный JSON. Записать ID проверки,
   хэш нормализованного набора, версию модели и параметры. После обновления страницы
   открыть отчёт в «Последние сохранённые проверки».
6. **12–15 минут.** Показать обычный будущий прогноз, категории, предупреждения и
   сценарий. Эта отдельная историческая проверка не изменяет рабочие прогнозы.

Если задача завершилась с ошибкой, сохранить код; повтор тех же параметров возобновит
исчерпавшее попытки задание. Не удалять импорт или БД ради повторного запуска.

## Что объяснить экспертам

- Модель каждого окна получает только прошлое. Будущие операции используются
  отдельно для вычисления факта. Вход фиксируется до постановки в очередь.
- MAE и RMSE выражены в рублях, MSE — в рублях в квадрате. Это ошибки денег.
- Accuracy/precision/recall/F1 относятся к событию отрицательного EOD.
  Есть отдельные матрицы для ежедневного минуса по медиане, ежедневного минуса
  по вероятности и появления нового минуса за целый горизонт. Их нельзя смешивать.
- Уже отрицательный старт не считается новым кассовым разрывом горизонта.
- ROC-AUC требует оба класса. Если минусов нет, некоторые метрики не определены:
  интерфейс показывает причину, а не выдуманные 100%. Для категоризации это не метрики.
- Вероятности — оценки действующей модели, ещё не откалиброванные; Brier оценивает
  их ошибку, а наблюдаемое покрытие p10–p90 проверяет интервалы на данном файле.
- Без подтверждения полноты считаются только доступные фактические остатки.
  Несверка потока и EOD блокирует восстановление пропущенных остатков и оценку потоков.
- Проверка statement-only исключает плановые платежи: исторические изменения
  обязательств не восстановлены. Она не доказывает качество всех сценариев с планами.
- При отсутствии будущего факта показываем прогноз; метрики — на историческом
  отложенном интервале. Качество на ещё неизвестном контрольном наборе заранее неизвестно.

## Вызов для интеграции Данила

```json
{
  "account_id": "UUID счёта после импорта",
  "as_of": "2024-03-10",
  "horizon_days": 10,
  "folds": 3,
  "threshold": 0.5,
  "seed": 42,
  "complete_statement": false
}
```

POST `/api/v1/companies/{company_id}/evaluations`, cookie-сессия owner и обычный
`X-CSRF-Token`. Ответ 202 содержит ID. Далее GET `/api/v1/evaluations/{id}` до
`succeeded`/`failed`. При наличии SHA-256 файла можно добавить `source_sha256`
(64 строчных hex-символа); он помечается как предоставленный импортёром.
Хэш нормализованных данных сервер вычисляет независимо.
Схема опубликована в `specs/openapi.json`. Основной UI уже подключён к этим API.
